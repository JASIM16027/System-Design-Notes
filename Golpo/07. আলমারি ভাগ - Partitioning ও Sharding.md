## Cache যেখানে হার মানলো

```
⚠️  Database disk usage: 92%
⚠️  Write latency: 340ms (স্বাভাবিক: 8ms)
```

তানহা প্রথমে ভাবলো — cache বাড়িয়ে দিই।

কিন্তু কয়েক মিনিট ভেবেই বুঝলো, **cache এখানে কোনো কাজেই আসবে না।**

Boltu ভাই ব্যাপারটা এক লাইনে বললো —

> **"Cache পড়ার সমস্যা মেটায়। কিন্তু লেখা তো cache করা যায় না — লেখা ডাটাবেসে যেতেই হবে। আর তোর ডাটাবেস একটাই।"**

তানহার সমস্যা এখন দুটো, আর দুটোই cache-এর নাগালের বাইরে:

**১. জায়গা শেষ।** ২ কোটি ১০ লাখ নোট, তাদের metadata, download-এর ইতিহাস — ডিস্ক ৯২% ভরা। আরো বড় ডিস্ক নেওয়া যায়, কিন্তু সেটা সাময়িক সমাধান।

**২. লেখা ধীর হয়ে যাচ্ছে।** সব লেখা ওই একটা মেশিনেই যাচ্ছে। যত row বাড়ছে, প্রতিটা INSERT-এ index update করতে তত সময় লাগছে।

## প্রথমে সহজ ধাপ — আলমারির ভিতরে তাক বানাও

Boltu ভাই বললো — "সরাসরি সবচেয়ে কঠিন সমাধানে যাস না। আগে দেখ সহজ কিছুতে কাজ হয় কিনা।"

তানহার সবচেয়ে বড় টেবিল ছিল `downloads` — কে কখন কোন নোট নামিয়েছে। এখানে **৩১ কোটি row**।

যেকোনো query এখানে ভয়ংকর ধীর।

কিন্তু তানহা খেয়াল করলো একটা জিনিস — তার query গুলোর **৯৯% আসলে শুধু গত এক মাসের data চায়**। কেউ দুই বছর আগের download-এর হিসাব দেখতে চায় না।

তবু ডাটাবেসকে প্রতিবার পুরো ৩১ কোটি row-এর মধ্যে খুঁজতে হচ্ছে।

**সমাধান — টেবিলটাকে মাস অনুযায়ী ভাগ করে দাও:**

```
downloads  (৩১ কোটি row — একটা দানব)
    │
    │  ভাগ করার পর
    ▼
downloads_2024_09   (৪২ লাখ)
downloads_2024_10   (৫১ লাখ)
downloads_2024_11   (৬৩ লাখ)
downloads_2024_12   (৭১ লাখ)   ← বেশিরভাগ query শুধু এখানেই আসে
```

এখন কেউ যদি লেখে:

```sql
SELECT * FROM downloads WHERE created_at >= '2024-12-01';
```

ডাটাবেস দেখে বলে — "ও, এটা তো শুধু ডিসেম্বরের ব্যাপার" — আর বাকি ৩০ কোটি row **ছুঁয়েও দেখে না**।

এর নাম **Partition Pruning** — অপ্রয়োজনীয় অংশ ছেঁটে ফেলা।

### গুরুত্বপূর্ণ কথা

**এটা এখনো একটাই ডাটাবেস সার্ভার।** শুধু ভিতরে গুছিয়ে রাখা।

আলমারিটা একটাই, শুধু ভিতরে তাক বানানো হয়েছে — জামাকাপড় এক গাদায় না রেখে মাস অনুযায়ী আলাদা তাকে।

**বোনাস সুবিধা:** দুই বছরের পুরনো data মুছতে চাইলে আগে `DELETE` চালাতে হতো, যেটা ঘণ্টার পর ঘণ্টা লাগতো আর ডাটাবেস আটকে রাখতো। এখন?

```sql
DROP TABLE downloads_2022_11;    -- এক সেকেন্ড
```

পুরো তাকটা তুলে ফেলে দাও।

### দুই ধরনের partition

**Horizontal (row ভাগ)** — উপরের উদাহরণ। row গুলোকে ভাগ করা।

**Vertical (column ভাগ)** — তানহার `users` টেবিলে ৩৪টা column ছিল, কিন্তু ৯০% query-তে লাগতো মাত্র ৪টা (id, name, email, avatar)। বাকি ৩০টা (bio, settings, preferences...) শুধু জায়গা খাচ্ছিল।

```
users_basic    (id, name, email, avatar)      ← ছোট, প্রায় সব query-তে লাগে
users_details  (bio, settings, preferences)   ← বড়, কদাচিৎ লাগে
```

ছোট টেবিল মানে একটা disk page-এ বেশি row ধরে, তাই পড়া দ্রুত।

## কিন্তু ছয় মাস পর তাকও ভরে গেলো

Partitioning তানহাকে ছয় মাস সময় দিয়েছিল। তারপর আবার একই অ্যালার্ট।

এবার আর কোনো উপায় নেই। **আলমারিটাই ছোট পড়ে গেছে।**

Boltu ভাই গম্ভীর হয়ে বললো —

> "এবার তোকে **Sharding** করতে হবে। কিন্তু শোন — এইটা সবচেয়ে কঠিন সিদ্ধান্ত যেটা তুই নিবি। একবার ভুল করলে ঠিক করতে মাস লেগে যাবে। তাই তাড়াহুড়ো করিস না।"

### Sharding মানে কী

Data-টাকে টুকরো করে **সম্পূর্ণ আলাদা আলাদা ডাটাবেস সার্ভারে** ভাগ করে দেওয়া।

```
              ┌──────────────────┐
   App ──────►│  কোন shard-এ?    │
              └────────┬─────────┘
      ┌────────────────┼────────────────┐
      ▼                ▼                ▼
 ┌─────────┐      ┌─────────┐      ┌─────────┐
 │ Shard-1 │      │ Shard-2 │      │ Shard-3 │
 │ আলাদা   │      │ আলাদা   │      │ আলাদা   │
 │ সার্ভার │      │ সার্ভার │      │ সার্ভার │
 └─────────┘      └─────────┘      └─────────┘
   ১/৩ data        ১/৩ data        ১/৩ data
```

**Partitioning vs Sharding — পার্থক্যটা এক লাইনে:**

| | Partitioning | Sharding |
|---|---|---|
| কোথায় | একই সার্ভারের ভিতরে | আলাদা আলাদা সার্ভারে |
| উপমা | এক আলমারিতে তাক | আলাদা আলাদা আলমারি |
| উদ্দেশ্য | query দ্রুত করা | জায়গা ও লেখার ভার ভাগ করা |
| JOIN কাজ করে? | ✅ স্বাভাবিকভাবে | ❌ করে না |
| জটিলতা | কম, DB নিজেই সামলায় | অনেক বেশি |

## সবচেয়ে গুরুত্বপূর্ণ সিদ্ধান্ত — কীসের ভিত্তিতে ভাগ করবে

এই একটা সিদ্ধান্তের উপর সবকিছু নির্ভর করে। একে বলে **Shard Key** বাছা।

তানহা তিনবার চেষ্টা করলো।

### ❌ চেষ্টা ১ — বিভাগ (department) দিয়ে

```
Shard-1: CSE, EEE
Shard-2: BBA, Economics
Shard-3: Philosophy, History, বাকি সব
```

Boltu ভাই একটা প্রশ্ন করলো — "তোর ডাটাবেসে কয়টা CSE-র student আর কয়টা Philosophy-র?"

তানহা query চালিয়ে দেখলো:

```
CSE:         ১৪,২০,০০০ user
EEE:          ৮,৯০,০০০
BBA:          ৬,৪০,০০০
Philosophy:      ৩২,০০০   😬
```

```
Shard-1:  ████████████████████████  ২৩ লাখ  (ফেটে যাবে)
Shard-2:  ██████████                ১১ লাখ
Shard-3:  ██                         ২ লাখ  (খালি পড়ে থাকবে)
```

**এর নাম Hotspot** — একটা shard-এ অস্বাভাবিক চাপ, বাকিরা অলস।

### ❌ চেষ্টা ২ — ভর্তির সাল দিয়ে

```
Shard-1: ২০১৮-২০১৯ ব্যাচ
Shard-2: ২০২০-২০২১ ব্যাচ
Shard-3: ২০২২-২০২৩ ব্যাচ
```

এবার সমস্যাটা আরো সূক্ষ্ম। Data মোটামুটি সমানভাবে ভাগ হলো ঠিকই, কিন্তু —

**নতুন সব user যাচ্ছে সর্বশেষ shard-এ। মানে সব নতুন লেখা একটা shard-এ।**

পুরনো shard গুলো শুধু পড়ার কাজ করছে, আর শেষ shard-টা সব লেখার ভার একা বইছে। যে সমস্যা সমাধান করতে sharding করা, সেটাই রয়ে গেলো।

### ✅ চেষ্টা ৩ — user_id দিয়ে

```
shard = hash(user_id) % 3
```

Boltu ভাই মাথা নেড়ে বললো — "এইটা ঠিক আছে। কারণ দেখ —"

| ভালো shard key-র শর্ত | user_id কি পূরণ করে? |
|---|---|
| **অনেক আলাদা মান আছে** (high cardinality) | ✅ ৫০ লাখ আলাদা মান |
| **সমানভাবে ছড়ায়** | ✅ hash করার পর প্রায় নিখুঁত সমতা |
| **Query-র সাথে মেলে** | ✅ "পড়ুয়া"-র বেশিরভাগ query একজন user-কে নিয়েই |

শেষ শর্তটা সবচেয়ে গুরুত্বপূর্ণ। "আমার আপলোড করা নোট", "আমার download-এর ইতিহাস" — এসব query-তে `user_id` থাকে, তাই **একটা shard-এই কাজ শেষ**।

Shard key যদি query-র সাথে না মিলতো, তাহলে প্রতিটা query-কে **সব shard-এ** যেতে হতো — আর তাতে sharding-এর কোনো লাভই থাকতো না।

> **Boltu ভাইয়ের সতর্কবাণী:** *"Shard key একবার বসিয়ে দিলে বদলানো মানে পুরো data নতুন করে সাজানো। মাস লেগে যাবে, তাও system চালু রেখে। তাই এই সিদ্ধান্তটা দশবার ভেবে নে।"*

## আর তারপর যে সমস্যাটা তানহাকে হতভম্ব করলো

ছয় মাস পর তানহার আরো একটা shard লাগলো। ৩ থেকে ৪।

সে নিরীহভাবে config-এ `% 3` বদলে `% 4` করলো।

আর তারপর হিসাব করে দেখলো — কতগুলো user-এর ঠিকানা বদলাবে?

```
user_id = 1001:   hash % 3 = 2  →  hash % 4 = 1   ❌ সরাতে হবে
user_id = 1002:   hash % 3 = 0  →  hash % 4 = 3   ❌ সরাতে হবে
user_id = 1003:   hash % 3 = 1  →  hash % 4 = 0   ❌ সরাতে হবে
user_id = 1004:   hash % 3 = 2  →  hash % 4 = 2   ✅ ঠিক আছে
...
```

**প্রায় ৭৫% data-র জায়গা বদলে যাচ্ছে।**

টেরাবাইটের পর টেরাবাইট data সরাতে হবে — আর সেটাও সাইট চালু রেখে, user-দের কিছু বুঝতে না দিয়ে।

তানহা মাথায় হাত দিয়ে বসে পড়লো।

### সমাধান — Consistent Hashing

Boltu ভাই বললো — "তুই `%` ব্যবহার করছিস, এইটাই সমস্যা। কারণ `%`-এ সার্ভারের **মোট সংখ্যাটা** ঢুকে আছে। সংখ্যা বদলালেই সব হিসাব বদলে যায়।

**সংখ্যাটা হিসাব থেকে সরিয়ে দে।**"

কল্পনা করো একটা বৃত্ত:

```
                    ০
              ┌─────┴─────┐
         ┌────┘           └────┐
      ┌──┘     Shard-A         └──┐
    ┌─┘        (৫০)              └─┐
   │                                │
Shard-D                          Shard-B
 (৮০০)                            (৩০০)
   │                                │
    └─┐                           ┌─┘
      └──┐    Shard-C         ┌───┘
         └────┐  (৬০০)   ┌────┘
              └──────────┘
```

**নিয়মটা সহজ:** প্রতিটা key কেও hash করে বৃত্তে বসাও, তারপর **ঘড়ির কাঁটার দিকে এগিয়ে প্রথম যে shard পাও, সেখানে যাও।**

```
user hash = ১৫০  →  এগোও  →  Shard-B (৩০০) পেলাম
user hash = ৭০০  →  এগোও  →  Shard-D (৮০০) পেলাম
```

**এখানে কোথাও shard-এর মোট সংখ্যা ব্যবহারই হয়নি।** এটাই মূল চাবিকাঠি।

এবার নতুন Shard-E যোগ করো, ধরো ৪৫০-এ:

```
আগে:  ৩০০ থেকে ৬০০ পর্যন্ত সব  →  Shard-C
এখন:  ৩০০ থেকে ৪৫০            →  Shard-E   ← শুধু এইটুকু সরলো
      ৪৫০ থেকে ৬০০            →  Shard-C   ← অপরিবর্তিত
```

**বাকি সব shard-এর একটা key-ও নড়লো না।**

৭৫%-এর বদলে সরলো মাত্র **২৫%** (গড়ে ১/N অংশ)।

### একটা বাড়তি চাল — Virtual Node

তানহা প্রথম চেষ্টায় দেখলো shard গুলো বৃত্তে সমানভাবে বসছে না — কারো ভাগে বৃত্তের বিশাল অংশ পড়ে যাচ্ছে।

সমাধান: প্রতিটা shard-কে বৃত্তে **একবার না, ১৫০ বার** বসাও (`Shard-A#1`, `Shard-A#2`, ... `Shard-A#150`)।

এতে দুটো লাভ —
১. অনেক ছোট ছোট টুকরায় ভাগ হওয়ায় বণ্টন প্রায় নিখুঁত সমান হয়
২. একটা shard মরলে তার ভার **একজনের ঘাড়ে না পড়ে সবার মধ্যে ছড়িয়ে যায়**

📖 *গভীরে যেতে চাইলে: [19. Consistent Hashing](../19.%20Consistent%20Hashing.md)*

---

## যে দামটা তানহাকে দিতে হলো

Sharding-এর পর তার কোডে তিনটা জিনিস ভেঙে পড়লো।

### ১. JOIN আর কাজ করে না

আগে এক লাইনে যা হতো:

```sql
SELECT n.*, u.name FROM notes n JOIN users u ON n.user_id = u.id;
```

এখন user Shard-1-এ, তার নোট Shard-3-এ — SQL এদের জুড়তেই পারে না।

**সমাধান:** দুবার query করে অ্যাপ্লিকেশনে নিজে মিলিয়ে নেওয়া। কোড লম্বা হলো, কিন্তু উপায় নেই।

### ২. "মোট কতজন user?" — এখন কঠিন

আগে `SELECT COUNT(*)`. এখন প্রতিটা shard-এ আলাদা করে জিজ্ঞেস করে যোগ করতে হয়। একে বলে **scatter-gather**, আর এটা ধীর।

তানহা এই সংখ্যাগুলো আলাদা করে হিসাব করে একটা জায়গায় রেখে দিলো, প্রতি ঘণ্টায় update হয়।

### ৩. আর সবচেয়ে অদ্ভুত সমস্যা — ID সংঘর্ষ

Sharding-এর পরদিন একটা ভয়ানক bug ধরা পড়লো।

```
Shard-1 এ নতুন নোট তৈরি হলো  →  id = 1
Shard-2 এ নতুন নোট তৈরি হলো  →  id = 1   😱
Shard-3 এ নতুন নোট তৈরি হলো  →  id = 1   😱
```

প্রতিটা shard তো আলাদা ডাটাবেস — প্রত্যেকে স্বাধীনভাবে ১ থেকে গোনা শুরু করেছে!

`poruya.com/notes/1` — এখন তিনটা আলাদা নোট বোঝাতে পারে।

**সমাধান তিনটা, তানহা তৃতীয়টা নিলো:**

| উপায় | সুবিধা | অসুবিধা |
|---|---|---|
| UUID | সহজ, নিশ্চিত unique | বড় (৩৬ অক্ষর), এলোমেলো তাই index-এ খারাপ |
| প্রতি shard-কে আলাদা range | সহজ | range শেষ হলে আবার ভাগ করতে হয় |
| **Snowflake ID** ⭐ | unique, সময় অনুযায়ী sorted, কোনো কেন্দ্রীয় সমন্বয় লাগে না | একটু বেশি code |

**Snowflake ID কীভাবে কাজ করে:**

```
৬৪ bit-এর একটা সংখ্যা:

[  ৪১ bit: timestamp  ][ ১০ bit: মেশিন নং ][ ১২ bit: ক্রমিক ]

সময়        → তাই স্বাভাবিকভাবেই sorted
মেশিন নং    → তাই দুই মেশিন কখনো একই ID বানাবে না
ক্রমিক      → একই মিলিসেকেন্ডে অনেকগুলো বানানো যায়
```

কোনো মেশিনকে কারো সাথে কথা বলতে হয় না, তবু ID কখনো সংঘর্ষ করে না। Twitter এটা বানিয়েছিল, আর এখন প্রায় সবাই এটাই ব্যবহার করে।

## Sharding-এর আগে যা যা করা উচিত

Boltu ভাই তানহাকে একটা ক্রম মুখস্থ করিয়ে দিলো। **Sharding সবার শেষে।**

```
১. Index ঠিক করো          ← সবচেয়ে সস্তা, প্রায়ই এখানেই ৮০% সমস্যা মেটে
        ↓
২. Slow query খুঁজে ঠিক করো  ← N+1 problem, অপ্রয়োজনীয় JOIN
        ↓
৩. Cache বসাও              ← অধ্যায় ৬
        ↓
৪. মেশিন বড় করো             ← সহজ, দ্রুত
        ↓
৫. Read replica যোগ করো     ← পরের অধ্যায়
        ↓
৬. Partitioning             ← এক সার্ভারের ভিতরেই
        ↓
৭. Sharding                 ← ⚠️ শেষ অস্ত্র
```

> **"Interview-তে যদি কেউ সরাসরি 'sharding করবো' বলে, সে খারাপ উত্তর দিলো। ধাপে ধাপে যাওয়াটাই সঠিক উত্তর।"**

---

## তানহা যা শিখলো

**১. Cache পড়ার সমস্যা মেটায়, লেখার না।** লেখা scale করতে হলে data ভাগ করতেই হবে।

**২. Partitioning সহজ, Sharding কঠিন।** আগে partitioning চেষ্টা করো — অনেক সময় সেটাই যথেষ্ট।

**৩. Shard key বাছাই সবচেয়ে গুরুত্বপূর্ণ সিদ্ধান্ত।** তিনটা শর্ত — অনেক আলাদা মান, সমান বণ্টন, আর query-র সাথে মিল।

**৪. `hash % N` ব্যবহার করো না** — N বদলালে সব ভেঙে যাবে। Consistent Hashing ব্যবহার করো।

**৫. Sharding করলে JOIN, COUNT আর auto-increment ID — তিনটাই হারাবে।** এই দামটা দিতে প্রস্তুত থাকো।
