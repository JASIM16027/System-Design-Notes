## তানহার লজ্জার ইতিহাস

তিনটা সার্ভার চালু হলো। সবগুলো stateless। সব ঠিক।

কিন্তু user জানবে কী করে কোন সার্ভারে যেতে হবে?

তানহা যা করলো, সেটা এখন মনে পড়লে সে মুখ ঢাকে।

সে তিনটা আলাদা ডোমেইন কিনলো, আর ফেসবুক গ্রুপে পোস্ট দিলো:

> *"সাইট slow লাগলে poruya2.com অথবা poruya3.com এ চেষ্টা করুন 🙏"*

```
poruya.com   →  Server-1
poruya2.com  →  Server-2
poruya3.com  →  Server-3
```

**ফলাফল?**

সবাই স্বাভাবিকভাবেই প্রথম লিংকটাতেই ক্লিক করলো। কে কষ্ট করে দ্বিতীয় ঠিকানা লিখবে?

```
Server-1:  ████████████████████████  ৯৪% CPU  😵 মরে যাচ্ছে
Server-2:  ██                         ৪% CPU  😴 ঘুমাচ্ছে
Server-3:  █                          ২% CPU  😴 ঘুমাচ্ছে
```

তিনটা সার্ভারের ভাড়া দিচ্ছে, কাজ করছে একটা।

তার উপর যারা দ্বিতীয় লিংকে গিয়েছিল, তারা আবার login করতে বাধ্য হলো (আলাদা ডোমেইন মানে আলাদা cookie)। মানে যে সমস্যা সে গত সপ্তাহে সমাধান করেছিল, সেটাই নতুন রূপে ফিরে এলো।

তানহা Boltu ভাইকে screenshot পাঠালো।

Boltu ভাইয়ের উত্তর এলো এক লাইনে:

> *"তুই হলের গেটে দাঁড়িয়ে সবাইকে বলছিস — 'ভাই, তিনটা রেজিস্টার খাতা আছে, যেটায় ইচ্ছা নাম লিখেন।' কী হবে বল তো?"*

## দারোয়ান চাচা

Boltu ভাই ব্যাখ্যা করলো —

"তোদের হলের গেটে দারোয়ান চাচা বসে থাকেন, ঠিক? তিনটা খাতা তাঁর সামনে।

কেউ ঢুকতে গেলে চাচা কী করেন? সবাইকে এক খাতায় লিখতে দেন? না। উনি এক নজর দেখেন **কোন খাতায় লাইন কম**, আর বলেন — 'আপনি ওই তিন নম্বরে যান।'

**তুই যেটা বানাতে ভুলে গেছিস, সেটাই ওই দারোয়ান চাচা। তার নাম Load Balancer।**"

```
                    ┌──────────────────────┐
   সব User ────────►│    Load Balancer     │  ← একটাই ঠিকানা
                    │      poruya.com      │     poruya.com
                    └──────────┬───────────┘
           ┌───────────────────┼───────────────────┐
           ▼                   ▼                   ▼
      ┌─────────┐        ┌─────────┐        ┌─────────┐
      │Server-1 │        │Server-2 │        │Server-3 │
      │10.0.0.1 │        │10.0.0.2 │        │10.0.0.3 │
      └─────────┘        └─────────┘        └─────────┘
              ↑ এই IP গুলো বাইরের কেউ জানেই না
```

তানহা তিনটা ডোমেইন বাতিল করলো। এখন শুধু `poruya.com`। ভিতরে তিনটা না তিরিশটা সার্ভার আছে — **user জানেই না, জানার দরকারও নেই।**

এটাই load balancer-এর প্রথম জাদু: **ভিতরের জটিলতাটা লুকিয়ে ফেলা।**

## চাচা ঠিক করেন কীভাবে কাকে কোথায় পাঠাবেন

তানহা Nginx-এর config খুলে দেখলো কয়েকটা অপশন আছে। প্রতিটার আলাদা যুক্তি।

### ১. Round Robin — সিরিয়াল ধরে

সবচেয়ে সহজ। একজন একজন করে ঘুরিয়ে ঘুরিয়ে।

```
Request-১ → Server-1
Request-২ → Server-2
Request-৩ → Server-3
Request-৪ → Server-1  (আবার শুরু)
```

*সুবিধা:* কোনো হিসাব রাখতে হয় না, তাই দ্রুত।
*অসুবিধা:* এটা ধরে নেয় **সব কাজ সমান ভারী**। বাস্তবে তা না।

### ২. Weighted Round Robin — শক্তি অনুযায়ী

তানহার একটা পুরনো সার্ভার আর দুটো নতুন শক্তিশালী সার্ভার ছিল। তাই সে ওজন বসিয়ে দিলো:

```
Server-1 (পুরনো)  weight = 1   → ২০% কাজ পাবে
Server-2 (নতুন)   weight = 2   → ৪০%
Server-3 (নতুন)   weight = 2   → ৪০%
```

### ৩. Least Connections — যার হাতে কম কাজ

এটাই "পড়ুয়া"-র জন্য সঠিক ছিল, আর কারণটা মজার।

তানহার সাইটে দুই ধরনের request আসে:

```
"নোটের তালিকা দেখাও"        →  ৩০ মিলিসেকেন্ড     (হালকা)
"৪০০ পাতার বই ডাউনলোড করো"  →  ৪৫ সেকেন্ড         (ভারী)
```

Round Robin-এ কী হয় দেখো:

```
Server-1 পেলো: ভারী, ভারী, ভারী   → ৩টা বড় ডাউনলোড চলছে, ধুঁকছে
Server-2 পেলো: হালকা, হালকা      → প্রায় খালি
```

সিরিয়াল ধরে ভাগ করলেও **কাজের ভার সমান হয় না**।

Least Connections এই সমস্যাটা মেটায় — সে গোনে এই মুহূর্তে কার হাতে কয়টা কাজ চলছে, আর সবচেয়ে খালি জনকে দেয়।

### ৪. IP Hash — একই লোক সবসময় একই জায়গায়

User-এর IP থেকে হিসাব করে সার্ভার ঠিক করা। একই IP মানে সবসময় একই সার্ভার।

*কখন লাগে:* যদি sticky session দরকার হয়। কিন্তু তানহা তো JWT ব্যবহার করছে, তাই তার এটা লাগেই না।

### সিদ্ধান্ত নেওয়ার সহজ ছক

| অবস্থা | কোনটা নেবে |
|---|---|
| সব সার্ভার একরকম, সব request একরকম | **Round Robin** |
| সার্ভারগুলোর ক্ষমতা আলাদা | **Weighted Round Robin** |
| Request-এর সময় ভিন্ন ভিন্ন (ছোট + বড়) | **Least Connections** ⭐ |
| Session সার্ভারে রাখতেই হবে | IP Hash (কিন্তু আগে stateless বানানোর চেষ্টা করো) |

তানহা `least_conn` বেছে নিলো। মাত্র একটা লাইন:

```nginx
upstream poruya_backend {
    least_conn;
    server 10.0.0.1;
    server 10.0.0.2;
    server 10.0.0.3;
}
```

## দ্বিতীয় জাদু — চাচা খবর রাখেন কে বেঁচে আছে

এক সপ্তাহ পর Server-2 হঠাৎ মরে গেলো। মাঝরাতে, কোনো কারণ ছাড়াই।

পরদিন সকালে তানহা যখন log দেখলো, সে অবাক হয়ে গেলো — **কোনো user অভিযোগ করেনি।** একটাও না।

কারণ load balancer নিজে থেকেই ব্যাপারটা সামলে নিয়েছে।

প্রতি কয়েক সেকেন্ড পর পর সে প্রতিটা সার্ভারকে একটা টোকা দেয়:

```
LB → Server-1:  GET /health   →  200 OK   ✅ ঠিক আছে
LB → Server-2:  GET /health   →  (নীরবতা)  ❌ বাদ
LB → Server-3:  GET /health   →  200 OK   ✅ ঠিক আছে
```

যে সার্ভার পরপর কয়েকবার উত্তর দেয় না, তাকে চাচা চুপচাপ লাইন থেকে সরিয়ে দেন। আর যেদিন সে আবার উত্তর দিতে শুরু করে, তাকে আবার ফিরিয়ে আনেন।

**User কিছুই টের পায় না।**

### কিন্তু "বেঁচে আছি" বলার দুটো মানে আছে

তানহা প্রথমে একটা বোকা health check বানিয়েছিল:

```javascript
app.get('/health', (req, res) => res.send('OK'));   // ❌ যথেষ্ট না
```

এটা শুধু বলে "আমার অ্যাপ চালু আছে"।

একদিন এমন হলো — একটা সার্ভারের **ডাটাবেস connection** নষ্ট হয়ে গেছে। অ্যাপ দিব্যি চলছে, `/health` দিব্যি `200 OK` বলছে, কিন্তু যে user-ই ওখানে যাচ্ছে তার কাছে error আসছে।

Load balancer জানেই না যে সার্ভারটা আসলে অকেজো।

তানহা ঠিক করলো:

```javascript
app.get('/health', async (req, res) => {
  try {
    await db.query('SELECT 1');        // ডাটাবেস কি সাড়া দিচ্ছে?
    await storage.ping();              // ফাইল storage কি সাড়া দিচ্ছে?
    res.status(200).send('OK');
  } catch (e) {
    res.status(503).send('NOT READY'); // আমাকে কাজ দিও না
  }
});
```

> **শিক্ষা:** Health check-এর কাজ "অ্যাপ চলছে কিনা" বলা না — **"আমি কি সত্যিই কাজ নেওয়ার মতো অবস্থায় আছি"** সেটা বলা।

## তৃতীয় জাদু — যেটা তানহা আশাই করেনি

এতদিন "পড়ুয়া"-তে নতুন কোড দিতে গেলে তানহাকে ঘোষণা দিতে হতো — *"রাত ৩টায় ১০ মিনিট সাইট বন্ধ থাকবে।"*

Load balancer আসার পর সে আবিষ্কার করলো একটা কৌশল:

```
ধাপ ১:  Server-1 কে load balancer থেকে সরিয়ে নাও
        (নতুন request আর যাবে না, চলমানগুলো শেষ হোক)
ধাপ ২:  Server-1 এ নতুন কোড দাও, চালু করো, পরীক্ষা করো
ধাপ ৩:  Server-1 কে আবার ফিরিয়ে আনো
ধাপ ৪:  একইভাবে Server-2, তারপর Server-3

সারাক্ষণ অন্তত দুটো সার্ভার চালু ছিল।
User একজনও টের পায়নি। ✅
```

এর নাম **Rolling Deployment**। আর এটা কেবল তখনই সম্ভব, যখন তোমার একাধিক সার্ভার আর একটা load balancer আছে।

**বোনাস:** নতুন কোডে সমস্যা থাকলে? প্রথম সার্ভারেই ধরা পড়বে, বাকি দুটোতে আর দেওয়াই হবে না। ঝুঁকি ৩ ভাগের ১ ভাগে নেমে এলো।

## L4 না L7 — চাচা কতটা বোঝেন?

তানহা config ঘাঁটতে গিয়ে দুটো শব্দ দেখলো — Layer 4 আর Layer 7।

Boltu ভাই বোঝালো ডাকপিয়নের উদাহরণ দিয়ে —

**Layer 4 দারোয়ান** খামের উপরের ঠিকানাটা দেখেন। ভিতরে কী লেখা আছে খুলেও দেখেন না। শুধু "এই বাড়ির চিঠি" বুঝেই পৌঁছে দেন।
→ **অসম্ভব দ্রুত**, কিন্তু বোকা।

**Layer 7 দারোয়ান** খাম খুলে চিঠিটা পড়েন। দেখেন এটা কী বিষয়ে, কার জন্য, জরুরি কিনা — তারপর সিদ্ধান্ত নেন।
→ **বুদ্ধিমান**, কিন্তু ধীর।

তানহার এই জিনিসটা কাজে লাগলো যখন সে "পড়ুয়া"-কে ভাগ করা শুরু করলো:

```
/api/search/*     →  Search সার্ভারগুলোতে (বেশি CPU লাগে)
/api/upload/*     →  Upload সার্ভারগুলোতে (বেশি bandwidth লাগে)
/api/*            →  সাধারণ API সার্ভারগুলোতে
```

**এই কাজটা কেবল Layer 7 পারে**, কারণ URL দেখতে হলে খাম খুলতেই হবে।

| | Layer 4 | Layer 7 |
|---|---|---|
| কী দেখে | IP আর port | URL, header, cookie |
| গতি | খুব দ্রুত | তুলনামূলক ধীর |
| URL দেখে routing | ❌ | ✅ |
| SSL termination | ❌ | ✅ |
| উদাহরণ | AWS NLB | Nginx, AWS ALB |

তানহা Nginx ব্যবহার করছিল — সেটা Layer 7।

## SSL Termination — একটা বাড়তি উপহার

তানহার প্রতিটা সার্ভারে আলাদা করে HTTPS সার্টিফিকেট বসাতে হতো। তিনটা সার্ভার মানে তিন জায়গায় সার্টিফিকেট, আর প্রতি তিন মাসে তিন জায়গায় renew।

Load balancer আসার পর সে সবটা এক জায়গায় নিয়ে এলো:

```
User ──HTTPS (তালাবদ্ধ)──► Load Balancer ──HTTP (খোলা)──► Servers
                                ↑
                         এখানেই তালা খোলা হয়
```

**লাভ দুটো:**
১. সার্টিফিকেট একটা জায়গায় — renew করাও একবার
২. Encryption খোলার ভারী কাজটা সার্ভারদের করতে হয় না, তাদের CPU বাঁচে

*সতর্কতা:* Load balancer আর সার্ভারের মাঝের রাস্তাটা খোলা থাকে। ব্যক্তিগত network-এ এটা সাধারণত ঠিক আছে, কিন্তু ব্যাংকিং বা স্বাস্থ্য-তথ্যের ক্ষেত্রে ওই অংশটাও তালাবদ্ধ রাখতে হয়।

---

## কিন্তু চাচা নিজে ছুটি নিলে?

দুই সপ্তাহ পর তানহার মাথায় প্রশ্নটা এলো, আর সে ভয় পেয়ে গেলো।

সে এতদিন ধরে single point of failure দূর করার চেষ্টা করছিল। তিনটা সার্ভার বানালো, যাতে একটা মরলেও চলে।

**কিন্তু load balancer তো একটাই!**

সে মরলে তিনটা সার্ভার দিব্যি বেঁচে থাকবে — আর কেউ তাদের কাছে পৌঁছাতেই পারবে না।

সে যে সমস্যা সমাধান করতে চেয়েছিল, সেটাই এক ধাপ উপরে উঠে গেছে।

Boltu ভাই হাসলো — "বাহ, তুই নিজেই ধরে ফেলেছিস। এইটাই সবচেয়ে বেশি জিজ্ঞেস করা interview প্রশ্ন।"

**সমাধান — দুইজন দারোয়ান:**

```
              ┌──────────────────┐
    DNS ─────►│   Virtual IP     │  ← ডোমেইন এই IP-তে যায়
              └────────┬─────────┘
              ┌────────┴─────────┐
              ▼                  ▼
      ┌──────────────┐   ┌──────────────┐
      │  LB-Active   │◄─►│  LB-Standby  │
      │  (কাজ করছে)  │   │  (পাশে বসা)  │
      └──────────────┘   └──────────────┘
              প্রতি সেকেন্ডে heartbeat
```

দুটো load balancer একটা **ভাসমান IP** ভাগ করে নেয়। প্রতি সেকেন্ডে একে অপরকে জিজ্ঞেস করে "বেঁচে আছো?"

Active মরলে standby সাথে সাথে ওই IP নিজের নামে নিয়ে নেয়। কয়েক সেকেন্ডের মধ্যে সব স্বাভাবিক।

**সুখবর:** ক্লাউডে (AWS ELB, Cloudflare, GCP Load Balancer) এই পুরো ব্যাপারটা তারা নিজেরাই সামলায় — তুমি একটা load balancer দেখো, কিন্তু ভিতরে ওটা redundant।

---

## Load Balancer vs API Gateway — একটা বিভ্রান্তি

তানহা পড়তে গিয়ে দুটো শব্দ গুলিয়ে ফেলেছিল।

**Load Balancer** ঠিক করে — *"এই request কোন সার্ভারে যাবে?"*

**API Gateway** ঠিক করে — *"এই request পাঠানোর আগে ও পরে কী কী করতে হবে?"* — যেমন token যাচাই, rate limit, log রাখা, response জোড়া লাগানো।

Gateway সাধারণত load balancer-এর **উপরে** বসে, এবং নিজেও load balancing করতে পারে।

📖 *গভীরে যেতে চাইলে: [11. Load Balancer](../11.%20Load%20Balancer%20-%20Complete%20Guide.md), [6. API Gateway](../6.%20API%20Gateway%20Details.md)*

## তানহা যা শিখলো

**১. একাধিক সার্ভার মানেই স্বয়ংক্রিয়ভাবে ভালো না** — সামনে একজন দারোয়ান না থাকলে সবাই এক দরজাতেই ভিড় করবে।

**২. User একটাই ঠিকানা জানবে।** ভিতরে কয়টা সার্ভার, সেটা তার জানার বিষয় না।

**৩. Health check-ই আসল জাদু** — এটার কারণেই সার্ভার মরলেও কেউ টের পায় না। আর সেটা যেন গভীর হয় (ডাটাবেসও পরীক্ষা করে), ভাসাভাসা না।

**৪. Algorithm বাছো কাজের ধরন দেখে** — সব সমান হলে Round Robin, ভিন্ন হলে Least Connections।

**৫. Load balancer নিজেই যেন single point of failure না হয়** — সবসময় জোড়ায় রাখো।

## এবার একটা অন্যরকম সমস্যা

Load balancer বসলো। সব সুন্দর চলছে।

তারপর একদিন একটা অদ্ভুত bug রিপোর্ট এলো, যেটা তানহা তিন দিনেও ধরতে পারলো না —

> *"বড় PDF গুলো ৬০-৭০% পর্যন্ত ডাউনলোড হয়ে তারপর থেমে যায়। ছোটগুলো ঠিকঠাক নামে।"*

তানহা সার্ভারের log দেখলো — কোনো error নেই। ফাইলগুলো ঠিক আছে। ডিস্কে জায়গা আছে।

তবু কিছু একটা ভুল হচ্ছে।

Boltu ভাই তাকে জিজ্ঞেস করলো একটা অদ্ভুত প্রশ্ন —

> *"আচ্ছা, তুই কি জানিস তোর সার্ভার আর user-এর ব্রাউজারের মাঝখানে আসলে কী ঘটে? পুরো ব্যাপারটা?"*

তানহা চুপ করে রইলো।

সে জানতো না।
