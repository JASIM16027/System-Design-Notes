## তানহার প্রথম architecture

"পড়ুয়া"-র প্রথম version-টা কেমন ছিল, জানো?

মাসে পাঁচশো টাকার একটা ক্লাউড সার্ভার। ২ CPU, ৪ GB RAM, ৪০ GB ডিস্ক। ব্যস।

আর তার ভিতরে **সবকিছু**।

```
┌───────────────────────────────────────────┐
│         একটা মাত্র কম্পিউটার               │
│                                           │
│   ┌─────────────────────────────────┐     │
│   │   Web Application (Node.js)     │     │
│   └─────────────────────────────────┘     │
│                                           │
│   ┌─────────────────────────────────┐     │
│   │   Database (PostgreSQL)         │     │
│   └─────────────────────────────────┘     │
│                                           │
│   ┌─────────────────────────────────┐     │
│   │   /uploads ফোল্ডার              │     │
│   │   (সব PDF এখানে)                │     │
│   └─────────────────────────────────┘     │
└───────────────────────────────────────────┘
```

কোনো load balancer নেই। কোনো cache নেই। কোনো CDN নেই। কোনো backup সার্ভার নেই।

একটা মেশিন, তার ভিতরে অ্যাপ, তার ভিতরে ডাটাবেস, তার ভিতরে একটা ফোল্ডারে সব ফাইল।

এখন তোমাকে একটা প্রশ্ন করি।

**এটা কি একটা খারাপ design?**

---

## উত্তরটা তোমাকে অবাক করবে

না। এটা ছিল **নিখুঁত** design।

শোনো কেন।

তখন "পড়ুয়া"-র user সংখ্যা ছিল ৫ জন। পাঁচ। দিনে সর্বোচ্চ ২০-৩০টা request আসতো। সবচেয়ে ব্যস্ত মুহূর্তে হয়তো দুজন একসাথে সাইটে থাকতো।

এই কাজের জন্য ২ CPU আর ৪ GB RAM **অতিরিক্ত** ছিল। সার্ভারটা দিনের ৯৮% সময় কার্যত ঘুমাতো।

এখন ভাবো, তানহা যদি প্রথম দিনেই এটা বানাতো —

```
তিনটা app server + load balancer (দুটো, redundancy-র জন্য)
+ Redis cache cluster
+ PostgreSQL primary + দুটো replica
+ Kafka message queue
+ CDN
+ Kubernetes
+ Prometheus monitoring
```

তাহলে কী হতো?

**এক:** মাসে পাঁচশো টাকার বদলে খরচ হতো মাসে পঁচিশ হাজার টাকা। একজন ছাত্রীর পক্ষে অসম্ভব।

**দুই:** তিন সপ্তাহের বদলে সময় লাগতো ছয় মাস। ততদিনে তার পরীক্ষা শেষ, উৎসাহও শেষ।

**তিন:** আর সবচেয়ে বড় কথা — এই পুরো জিনিসটা সে **কীভাবে ঠিক করতো** যখন কিছু ভাঙতো? ৫ জন user-এর জন্য বানানো একটা Kubernetes cluster-এ bug খুঁজতে যাওয়া মানে খড়ের গাদায় সুঁই খোঁজা, যেখানে খড়টাও তুমিই বসিয়েছো।

Boltu ভাই — তানহার সিনিয়র, যে একটা কোম্পানিতে দুই বছর ধরে কাজ করছে — এই ব্যাপারটা তাকে একটা লাইনে বুঝিয়েছিল:

> **"আজকের সমস্যার জন্য আজকের সমাধান বানা। কালকের সমস্যার জন্য কালকের সমাধান বানাবি — কারণ কালকের সমস্যাটা আসলে কী হবে, সেটা তুই আজকে জানিসই না।"**

---

## তাহলে System Design জিনিসটা কী?

অনেকে ভাবে system design মানে বড় বড় box আঁকা আর তার মাঝে তীর চিহ্ন দেওয়া। ভাবে system design মানে যত বেশি component, তত ভালো।

**দুটোই ভুল।**

System design আসলে একটা প্রশ্নের উত্তর খোঁজা:

> **"আমার এখনকার প্রয়োজন কতটুকু, আর আমার এখনকার সমাধানের সীমা কোথায়?"**

লক্ষ্য করো — দুটো অংশ আছে।

**প্রথম অংশ: প্রয়োজন কতটুকু।** এটা না জানলে তুমি হয় কম বানাবে (তখন ভেঙে পড়বে), নয় বেশি বানাবে (তখন টাকা আর সময় নষ্ট হবে)।

**দ্বিতীয় অংশ: সীমা কোথায়।** এটাই আসল দক্ষতা। তানহার এক-সার্ভারের design ভালো ছিল — কিন্তু সেটার একটা **সীমা** ছিল। সেই সীমাটা কোথায়, সেটা জানা থাকলে যেদিন কাছাকাছি পৌঁছাবে, সেদিন আগেভাগে প্রস্তুত হওয়া যায়।

তানহা তখন সেটা জানতো না। তাই একদিন সে ধাক্কা খেয়েছিল। সেই গল্প পরের অধ্যায়ে।

---

## যে দুটো প্রশ্ন দিয়ে সব শুরু হয়

যেকোনো system-এর design শুরু হয় দুই ধরনের প্রশ্ন দিয়ে।

### ১. Functional Requirement — "কী কী করবে?"

এটা হলো **feature-এর তালিকা**। সিস্টেমটা আসলে কোন কাজগুলো করতে পারবে।

"পড়ুয়া"-র ক্ষেত্রে:

- ✅ User নোট আপলোড করতে পারবে
- ✅ বিষয়/বিভাগ/সাল দিয়ে খুঁজতে পারবে
- ✅ ডাউনলোড করতে পারবে
- ✅ Account খুলে login করতে পারবে

এটুকুই। এর বেশি কিছু না।

তানহা ইচ্ছে করেই অনেক কিছু **বাদ** দিয়েছিল — কমেন্ট নেই, রেটিং নেই, নোটিফিকেশন নেই, চ্যাট নেই। কারণ প্রথম version-এর কাজ feature দেখানো না, **সমস্যাটা সত্যিই আছে কিনা সেটা প্রমাণ করা**।

### ২. Non-Functional Requirement — "কেমনভাবে করবে?"

এটা feature না, এটা **মানের মাপকাঠি**। আর মজার ব্যাপার হলো — system design-এর প্রায় সব সিদ্ধান্ত আসলে এখান থেকেই আসে।

| প্রশ্ন | তানহার তখনকার উত্তর |
|---|---|
| কতজন ব্যবহার করবে? | ৫ জন, হয়তো ৫০ |
| কত দ্রুত হতে হবে? | ২ সেকেন্ডে পাতা খুললেই হলো |
| কতক্ষণ চালু থাকতে হবে? | রাতে এক ঘণ্টা বন্ধ থাকলেও কেউ টের পাবে না |
| Data হারালে কী হবে? | খারাপ, কিন্তু পৃথিবী ধ্বংস হবে না |
| বাজেট কত? | মাসে ৫০০ টাকা |

এখন এই উত্তরগুলো দেখে বলো — এই সিস্টেমের জন্য কি load balancer লাগে? Replica লাগে? Multi-region লাগে?

**লাগে না।** উত্তরগুলোই বলে দিচ্ছে এক সার্ভারই যথেষ্ট।

আর এখানেই আসল কথাটা:

> **Architecture তুমি ঠিক করো না। Requirement ঠিক করে দেয় architecture কেমন হবে।**

তিন বছর পর যখন "পড়ুয়া"-র user ৫০ লাখ, তখন এই টেবিলের উত্তরগুলো সম্পূর্ণ বদলে যাবে — আর তাই architecture-ও বদলে যাবে। কিন্তু সেটা তখন, এখন না।

## একটা হিসাব যা তানহা তখন করেনি (কিন্তু করা উচিত ছিল)

Boltu ভাই একবার তাকে একটা অভ্যাস শিখিয়েছিল — **কাগজে-কলমে দুই মিনিটের হিসাব**।

দেখো কত সহজ।

**ধরো "পড়ুয়া"-র ১০ হাজার user হলো।**

প্রত্যেকে দিনে গড়ে ২টা নোট দেখে:

```
দিনে মোট request = ১০,০০০ × ২ = ২০,০০০
এক দিনে সেকেন্ড    = ৮৬,৪০০

গড়ে প্রতি সেকেন্ডে request = ২০,০০০ ÷ ৮৬,৪০০ ≈ ০.২৩
```

প্রতি সেকেন্ডে **এক ভাগেরও কম** request! একটা সাধারণ সার্ভার এটা চোখ বন্ধ করে সামলাতে পারে।

**কিন্তু এখানেই ফাঁদ।**

সবাই কি সারাদিন সমানভাবে আসে? না। "পড়ুয়া"-তে সবাই আসে **পরীক্ষার আগের রাতে, রাত ৯টা থেকে ২টার মধ্যে**।

মানে দিনের সব traffic ৫ ঘণ্টায় জমা হয়। আর তার মধ্যেও সবচেয়ে ব্যস্ত এক ঘণ্টায় হয়তো ৪০% traffic আসে।

```
Peak QPS ≈ গড়ের ১০-২০ গুণ
```

এই একটা লাইন তানহা তখন জানতো না। আর ঠিক এই কারণেই এক রাতে তার সাইট ধসে পড়েছিল।

## Over-engineering — নীরব ঘাতক

এই অধ্যায়ের সবচেয়ে গুরুত্বপূর্ণ কথাটা এখানে।

তুমি হয়তো ভাবছো — "আগে থেকে বড় করে বানিয়ে রাখলে সমস্যা কী? পরে তো কাজে লাগবে।"

সমস্যা তিনটা, আর তিনটাই মারাত্মক।

**১. তুমি ভুল জিনিসের জন্য প্রস্তুতি নেবে।**
তানহা ভেবেছিল তার সবচেয়ে বড় সমস্যা হবে **storage** — এত PDF কোথায় রাখবে? বাস্তবে প্রথম যেটা শেষ হয়েছিল সেটা ছিল **CPU**। সে যদি আগে থেকে বিশাল storage কিনে রাখতো, সেটা কোনো কাজেই আসতো না।

**২. প্রতিটা component একটা নতুন ভাঙার জায়গা।**
Load balancer যোগ করলে load balancer-ও একদিন ভাঙবে। Cache যোগ করলে cache-এর নিজস্ব সমস্যা আসবে (পুরনো data দেখানো, memory ভরে যাওয়া)। যা তোমার দরকার নেই, তা যোগ করা মানে বিনা কারণে ঝুঁকি কেনা।

**৩. জটিলতা তোমার গতি কেড়ে নেয়।**
একটা নতুন feature যোগ করতে যদি ৮টা service-এ কাজ করতে হয়, তাহলে তুমি মাসে যা করতে পারতে, তা করতে তিন মাস লাগবে। Startup এভাবেই মরে।

> **Boltu ভাইয়ের নিয়ম:** *"এখন যা আছে তার ১০ গুণ পর্যন্ত সামলাতে পারে — এমন design বানা। ১০০ গুণের চিন্তা করিস না, কারণ ততদিনে product-টাই বদলে যাবে।"*

## তানহা যা শিখলো

| ভুল ধারণা | বাস্তবতা |
|---|---|
| System design মানে জটিল architecture | System design মানে **সবচেয়ে সহজ সমাধান যেটা কাজ করে** |
| আগে থেকে সব বানিয়ে রাখা বুদ্ধিমানের কাজ | আগে থেকে বানানো মানে ভুল জিনিসের জন্য প্রস্তুতি |
| এক সার্ভার মানে খারাপ design | ৫ জন user-এর জন্য এক সার্ভারই **সঠিক** design |
| Architecture আগে ঠিক করি, পরে requirement | **Requirement-ই ঠিক করে দেয়** architecture |
