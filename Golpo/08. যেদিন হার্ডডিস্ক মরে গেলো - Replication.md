সকাল ৭টায় তানহা backup থেকে data ফেরানো শুরু করলো। ৩ TB data — restore হতে লাগলো **সাড়ে ছয় ঘণ্টা**।

দুপুর ২টায় সাইট আবার চালু হলো।

**হিসাবটা:**

```
সাইট বন্ধ ছিল:           ৯ ঘণ্টা ৪৮ মিনিট
স্থায়ীভাবে হারানো data:   ১৮ ঘণ্টার
প্রভাবিত user:            ১৭,০০,০০০
```

গত ১৮ ঘণ্টায় যারা নোট আপলোড করেছিল, নতুন অ্যাকাউন্ট খুলেছিল, বা কিছু বদলেছিল — **সব হারিয়ে গেছে**। ফেরানোর কোনো উপায় নেই।

তানহা সেদিন সারাদিন ক্ষমা চেয়ে মেসেজের উত্তর দিলো।

## Backup আর Replication — একই জিনিস না

তানহার একটা মৌলিক ভুল ধারণা ছিল। সে ভাবতো backup থাকলেই যথেষ্ট।

| | Backup | Replication |
|---|---|---|
| কী | নির্দিষ্ট সময়ের একটা ছবি | সারাক্ষণ চলমান copy |
| কতটা পুরনো | ঘণ্টা বা দিন | মিলিসেকেন্ড |
| ফেরাতে সময় | ঘণ্টার পর ঘণ্টা | সেকেন্ড |
| কী থেকে বাঁচায় | ভুল করে মুছে ফেলা, ransomware | হার্ডওয়্যার ব্যর্থতা |
| তখন সাইট | **বন্ধ** | **চালু** |

> **দুটোই লাগবে।** Backup বাঁচায় *মানুষের ভুল* থেকে (কেউ ভুল করে টেবিল drop করলে replica-তেও drop হয়ে যাবে!)। Replication বাঁচায় *যন্ত্রের ব্যর্থতা* থেকে।

## Replication — একটার বদলে অনেকগুলো

তানহা পরের সপ্তাহে পুরো সিস্টেম নতুন করে সাজালো।

```
                    ┌──────────────────┐
     সব লেখা ──────►│     Primary      │
                    └────────┬─────────┘
                             │ প্রতিটা পরিবর্তন
                             │ সাথে সাথে ছড়িয়ে যায়
            ┌────────────────┼────────────────┐
            ▼                ▼                ▼
      ┌──────────┐     ┌──────────┐     ┌──────────┐
      │Replica-1 │     │Replica-2 │     │Replica-3 │
      └────▲─────┘     └────▲─────┘     └────▲─────┘
           │                │                │
           └────────────────┴────────────────┘
                        সব পড়া
```

- **Primary** — সব লেখা এখানেই যায়
- **Replica** — Primary-র হুবহু copy, শুধু পড়ার কাজ করে

### এতে তিনটা লাভ একসাথে

**১. ব্যর্থতা থেকে বাঁচা (মূল উদ্দেশ্য)**
Primary মরলে একটা replica-কে promote করে দেওয়া হয়। ৯ ঘণ্টার বদলে **৩০ সেকেন্ড**।

**২. পড়ার ভার ভাগ হওয়া (বোনাস)**
"পড়ুয়া"-তে ৯৫% traffic-ই পড়ার। এখন সেটা তিনটা replica ভাগ করে নিচ্ছে। Primary শুধু লেখার কাজ নিয়ে থাকে, তাই লেখাও দ্রুত হলো।

**৩. Backup নেওয়া সহজ হওয়া (বোনাস)**
আগে backup নেওয়ার সময় ডাটাবেস ধীর হয়ে যেতো, তাই তানহা দিনে একবারই নিতো। এখন replica থেকে backup নেওয়া যায় — primary কিছুই টের পায় না। তাই এখন **প্রতি ঘণ্টায়** backup নেওয়া হয়।

### শুধু ডাটাবেস না — সবকিছু

তানহা এবার পুরো তালিকা ধরে ধরে দেখলো, কোথায় কোথায় একটামাত্র copy আছে:

| আগে | এখন |
|---|---|
| ১টা load balancer | ২টা (active + standby) |
| ৩টা app server | ৬টা, দুটো আলাদা zone-এ |
| প্রতি shard-এ ১টা DB | ১ primary + ২ replica |
| দিনে ১বার backup | ঘণ্টায় ১বার + আলাদা region-এ copy |
| সব এক availability zone-এ | তিনটা zone-এ ছড়ানো |

> **নিয়মটা সরল:** *এমন কোনো জিনিস থাকা যাবে না, যেটা একা মরলে সব মরে।*

## সাথে সাথে না পরে — দুই ধরনের Replication

তানহা config করতে গিয়ে একটা পছন্দের মুখে পড়লো।

### Synchronous — নিশ্চিত হয়ে তবেই

```
User লিখলো
   → Primary লিখলো
   → Replica-কে পাঠালো
   → Replica বললো "আমিও লিখেছি" ✅
   → তবেই user-কে "সফল" বলা হলো
```

**✅ কোনো data হারাবে না।** Primary মরার আগমুহূর্ত পর্যন্ত সব replica-তে আছে।
**❌ প্রতিটা লেখা ধীর।** Replica-র জন্য অপেক্ষা করতে হয়। আর replica ধীর হলে primary-ও আটকে যায়।

### Asynchronous — লিখেই এগিয়ে যাও

```
User লিখলো
   → Primary লিখলো
   → সাথে সাথে "সফল" বললো ✅
   → Replica-তে data পরে যাবে
```

**✅ লেখা দ্রুত।**
**❌ Primary হঠাৎ মরলে শেষ কয়েকটা লেখা হারাতে পারে।**

### তানহার সিদ্ধান্ত

সে **মাঝামাঝি পথ** নিলো — **Semi-synchronous**। অন্তত একটা replica নিশ্চিত করলেই যথেষ্ট, বাকিরা পরে ধরুক।

আর কিছু জায়গায় আলাদা নিয়ম:

| কী | পদ্ধতি | কারণ |
|---|---|---|
| নোট আপলোড | Semi-sync | একটু ধীর হলেও চলবে, কিন্তু হারানো চলবে না |
| Download counter | Async | দু-একটা গোনা মিস হলে কিছু যায় আসে না |
| Premium payment | **Sync** | এক পয়সাও হারানো যাবে না |

## আর তারপর একটা নতুন ভূত

Replication চালু হওয়ার এক সপ্তাহ পর অদ্ভুত অভিযোগ আসতে শুরু করলো:

> *"আপু, নোট আপলোড করলাম। 'সফল' লেখা দেখালো। কিন্তু আমার প্রোফাইলে গিয়ে দেখি নোটটা নাই!"*
> *"একটু পরে refresh করলে আবার চলে আসে। ভূতুড়ে ব্যাপার!"*

তানহা ভয় পেয়ে গেলো — data কি আবার হারাচ্ছে?

না। **Data হারাচ্ছে না। শুধু এখনো পৌঁছায়নি।**

```
১. User আপলোড করলো
   → Primary-তে লেখা হলো ✅
   → "সফল" দেখানো হলো

২. User সাথে সাথে প্রোফাইল পাতায় গেলো
   → এটা পড়ার কাজ, তাই Replica-তে গেলো

৩. কিন্তু Replica এখনো ০.৪ সেকেন্ড পিছিয়ে
   → নোটটা তখনো ওখানে পৌঁছায়নি

৪. User দেখলো — কিছু নেই  😱

৫. ২ সেকেন্ড পর refresh করলো
   → এবার পৌঁছে গেছে, দেখা যাচ্ছে
```

এই দেরিটার নাম **Replication Lag**। আর এই নির্দিষ্ট সমস্যাটার নাম **"Read Your Own Writes"**।

### সমাধান

Boltu ভাই বললো — "সহজ। যে নিজে কিছু লিখেছে, তাকে পরের কিছুক্ষণ **primary থেকেই পড়া**। অন্যরা replica থেকে পড়ুক — তাদের আধ সেকেন্ড দেরিতে দেখলে কিছু যায় আসে না।"

```javascript
async function getUserNotes(userId) {
  const justWrote = await redis.get(`recent_write:${userId}`);

  const db = justWrote
    ? primaryDB        // নিজে সদ্য লিখেছে → primary থেকে পড়াও
    : replicaDB;       // অন্য সবাই → replica

  return db.query('SELECT * FROM notes WHERE user_id = ?', [userId]);
}

// লেখার সময়:
await primaryDB.insert(note);
await redis.setex(`recent_write:${userId}`, 10, '1');   // ১০ সেকেন্ড
```

সমস্যা শেষ।

লক্ষ্য করো ব্যাপারটা — **তানহা সবার জন্য নিখুঁত consistency দেয়নি।** সে শুধু ওই একটামাত্র জায়গায় দিয়েছে যেখানে user সত্যিই পার্থক্যটা টের পেতো।

এটাই বাস্তব system design — **সব জায়গায় নিখুঁততা না, যেখানে দরকার সেখানে।**

## Failover — Primary মরলে কী হয়

তানহা এবার নিশ্চিত হতে চাইলো, primary মরলে সত্যিই দ্রুত ফিরে আসা যায় কিনা।

**স্বয়ংক্রিয় failover কীভাবে কাজ করে:**

```
১. একটা monitoring সিস্টেম প্রতি সেকেন্ডে primary-কে টোকা দেয়
২. পরপর কয়েকবার সাড়া না পেলে সে ধরে নেয় primary মৃত
৩. সবচেয়ে up-to-date replica-কে বেছে নেয়
৪. সেটাকে নতুন primary ঘোষণা করে
৫. বাকি replica-দের বলে "এখন থেকে ওকে অনুসরণ করো"
৬. অ্যাপকে নতুন ঠিকানা জানিয়ে দেয়
```

সময় লাগে **১০-৩০ সেকেন্ড**। ৯ ঘণ্টার তুলনায় কিছুই না।

### কিন্তু এখানে একটা ভয়ংকর ফাঁদ আছে

তানহা পড়তে গিয়ে **Split Brain** নামে একটা জিনিস আবিষ্কার করলো, আর শিউরে উঠলো।

```
পরিস্থিতি: primary আসলে মরেনি, শুধু network-এ সমস্যা হয়েছে

Monitoring ভাবলো:  "Primary মরে গেছে" → Replica-1 কে promote করলো
পুরনো Primary ভাবলো: "আমি তো দিব্যি বেঁচে আছি" → লেখা নিতে থাকলো

এখন দুইটা primary!
কিছু user পুরনোটায় লিখছে, কিছু নতুনটায়।

Network ঠিক হলে — কোনটা সঠিক? 🤯
```

দুই জায়গায় আলাদা আলাদা data। মেলানোর কোনো উপায় নেই। **এটা হার্ডডিস্ক নষ্ট হওয়ার চেয়েও খারাপ**, কারণ এখানে তুমি জানোই না কোন data-টা ঠিক।

**সমাধান — সংখ্যাগরিষ্ঠতার নিয়ম (Quorum):**

```
মোট node রাখো বিজোড় সংখ্যায় — ৩ বা ৫

Primary হতে হলে সংখ্যাগরিষ্ঠের সমর্থন লাগবে (৩-এর মধ্যে ২)

Network ভাগ হয়ে গেলে:
   বড় অংশ (২টা node)  → সংখ্যাগরিষ্ঠ আছে → primary বাছতে পারবে ✅
   ছোট অংশ (১টা node)  → সংখ্যাগরিষ্ঠ নেই → নিজে থেকে সরে দাঁড়াবে ✅

দুই দিকে দুইটা primary কখনোই হতে পারবে না।
```

সাথে **fencing** — পুরনো primary যাতে জোর করেও আর লিখতে না পারে, তার ক্ষমতা কেড়ে নেওয়া।

---

## তানহা যা শিখলো

**১. হার্ডওয়্যার মরবেই।** এটা "যদি"-র প্রশ্ন না, "কখন"-এর প্রশ্ন। এই মানসিকতা নিয়ে design করতে হয়।

**২. Backup আর Replication আলাদা জিনিস, দুটোই লাগে।** Backup বাঁচায় মানুষের ভুল থেকে, replication বাঁচায় যন্ত্রের ব্যর্থতা থেকে।

**৩. একটামাত্র copy কোথাও রাখবে না** — ডাটাবেস, load balancer, সার্ভার, কিছুই না।

**৪. Replication lag বাস্তব।** নিজের লেখা জিনিস দেখাতে হলে primary থেকে পড়াও — কিন্তু সবার জন্য না, শুধু যার দরকার তার জন্য।

**৫. Failover-এ Split Brain-এর ঝুঁকি থাকে।** Quorum আর fencing ছাড়া স্বয়ংক্রিয় failover বিপজ্জনক।

**৬. আর সবচেয়ে বড় কথা** — তানহা সেই রাতের পর একটা অভ্যাস করলো: প্রতি মাসে সে **ইচ্ছে করে** একটা সার্ভার বন্ধ করে দেখে সিস্টেম টিকে থাকে কিনা। কারণ যে failover কখনো পরীক্ষা করা হয়নি, সেটা আসলে failover না — সেটা একটা আশা।

## তারপর তানহা ভাবলো সব সমস্যা শেষ

Replication আছে, sharding আছে, cache আছে, CDN আছে, load balancer আছে।

"পড়ুয়া" এখন এত বড় যে সে ইউরোপেও একটা অঞ্চল খুললো — সেখানকার প্রবাসী শিক্ষার্থীদের জন্য।

দুই অঞ্চল, একে অপরের সাথে data sync করে।

আর তারপর এক দুপুরে ঘটলো এমন একটা ঘটনা, যেটা তানহাকে বুঝিয়ে দিলো — **কিছু সমস্যার আসলে কোনো সমাধান নেই।**

শুধু পছন্দ আছে।
