## এবার তানহা অন্ধভাবে সার্ভার বাড়ালো না

সাইট আবার ধীর। কিন্তু এবার তানহা আগের মতো আতঙ্কে সার্ভার upgrade করলো না।

সে এবার **মাপলো**।

কোডে কয়েকটা টাইমার বসিয়ে দেখলো একটা হোমপেজ request-এর সময় কোথায় কোথায় যাচ্ছে:

```
পুরো request:                        ৯৪০ ms
├── JWT যাচাই:                          ২ ms
├── template render:                    ১৮ ms
├── "সপ্তাহের জনপ্রিয় নোট" query:      ৮৬২ ms  🔴
├── "নতুন আপলোড" query:                 ৪১ ms
└── বাকি সব:                            ১৭ ms
```

**একটাই query। ৮৬২ মিলিসেকেন্ড। মোট সময়ের ৯২%।**

তানহা query-টা খুলে দেখলো:

```sql
SELECT n.*, u.name, COUNT(d.id) as download_count
FROM notes n
JOIN users u ON n.user_id = u.id
LEFT JOIN downloads d ON d.note_id = n.id
WHERE d.created_at > NOW() - INTERVAL '7 days'
GROUP BY n.id, u.name
ORDER BY download_count DESC
LIMIT 20;
```

কয়েক লাখ row ঘেঁটে, গুনে, সাজিয়ে, সবচেয়ে জনপ্রিয় ২০টা বের করা। ভারী কাজ, তাই ধীর হওয়াই স্বাভাবিক।

কিন্তু আসল সমস্যাটা ছিল অন্য জায়গায়।

## যে হিসাবটা তানহাকে থমকে দিলো

Boltu ভাই একটা প্রশ্ন করলো —

> *"এই query-র উত্তরটা কতক্ষণ পর পর বদলায়?"*

তানহা ভেবে বললো — "সপ্তাহের হিসাব তো... ঘণ্টায় হয়তো এক-দুইটা জায়গা এদিক-ওদিক হয়।"

> *"আর এই query টা দিনে কতবার চলে?"*

তানহা analytics খুলে দেখলো — হোমপেজে দিনে **১১ লাখ** visitor।

Boltu ভাই বললো — "তাহলে হিসাবটা কর।"

```
এই ভারী query চলছে:      দিনে ১১,০০,০০০ বার
উত্তর বদলাচ্ছে:           দিনে হয়তো ২৪ বার

মানে ১০,৯৯,৯৭৬ বার সে একই হিসাব করে
একই উত্তরটাই বের করছে।
```

তানহার মুখ শুকিয়ে গেলো।

তার ডাটাবেস দিনের ৯৯.৯৯% সময় **আগে যা বের করেছে, ঠিক সেটাই আবার বের করার কাজে ব্যস্ত**।

## রান্নাঘরের কৌটা

Boltu ভাই বললো —

"তুই রান্না করছিস। এক চিমটি লবণ লাগবে।

এখন যদি তুই প্রতিবার লবণ লাগলে বাজারে যাস, লবণ কিনিস, এক চিমটি দিস, বাকিটা বাজারে ফেরত দিয়ে আসিস — রান্না শেষ হবে কবে?

**লবণটা কিনে চুলার পাশে একটা কৌটায় রেখে দে।** যতবার লাগে, হাত বাড়ালেই পাবি।

তোর ডাটাবেস হলো বাজার — দূরে, ধীর, ভিড়।
আর Redis হলো **চুলার পাশের কৌটা** — হাতের নাগালে, তাৎক্ষণিক।"

```
Cache ছাড়া:
   App ──────────────────► Database      (৮৬২ ms, প্রতিবার)

Cache সহ:
   App ──► Redis ──► পেয়ে গেছি!  ফেরত   (২ ms)  ✅
            │
            └─ না পেলে ──► Database (৮৬২ ms)
                           তারপর কৌটায় রেখে দাও
```

## চার লাইনের জাদু

তানহা লিখলো:

```javascript
async function getPopularNotes() {
  // ১. আগে কৌটায় দেখো
  const cached = await redis.get('popular:weekly');
  if (cached) return JSON.parse(cached);          // ২ ms ✅

  // ২. না পেলে বাজারে যাও
  const notes = await db.query(HEAVY_QUERY);      // ৮৬২ ms

  // ৩. আর কৌটায় ভরে রাখো, ১০ মিনিটের জন্য
  await redis.setex('popular:weekly', 600, JSON.stringify(notes));

  return notes;
}
```

**ফলাফল:**

| | আগে | পরে |
|---|---|---|
| হোমপেজ লোড | ৯৪০ ms | **৬১ ms** |
| ডাটাবেসে ওই query | ১১,০০,০০০ বার/দিন | **১৪৪ বার/দিন** |
| ডাটাবেসের CPU | ৭৮% | **৯%** |

**১৪৪ কেন?** কারণ ১০ মিনিট পর পর একবার করে চলে — দিনে ২৪ × ৬ = ১৪৪ বার। বাকি সবাই কৌটা থেকে পায়।

এই কৌশলটার নাম **Cache-Aside** — অ্যাপ নিজে cache সামলায়। আগে cache দেখে, না পেলে ডাটাবেসে যায়, তারপর cache-এ রেখে দেয়। এটাই সবচেয়ে বেশি ব্যবহৃত পদ্ধতি।

## কেন RAM এত দ্রুত

তানহার প্রশ্ন ছিল — ৮৬২ ms থেকে ২ ms, এতটা পার্থক্য কেন?

Boltu ভাই একটা টেবিল দেখালো, যেটা প্রতিটা engineer-এর মুখস্থ থাকা উচিত:

| কোথা থেকে | সময় | যদি ১ সেকেন্ড ধরি |
|---|---|---|
| RAM (memory) | ১০০ ন্যানোসেকেন্ড | ১.৫ মিনিট |
| SSD | ০.১৫ মিলিসেকেন্ড | ১.৭ দিন |
| একই datacenter-এ network | ০.৫ মিলিসেকেন্ড | ৫.৮ দিন |
| ঘূর্ণায়মান ডিস্ক (HDD) | ১০ মিলিসেকেন্ড | ৪ মাস |

> **RAM থেকে পড়া ডিস্ক থেকে পড়ার চেয়ে প্রায় এক লক্ষ গুণ দ্রুত।**

Cache মানেই মূলত — **RAM-এ রাখা**।

## তারপর তিনটা বিপদ এলো

তানহা ভেবেছিল কাজ শেষ। পরের তিন সপ্তাহে সে শিখলো — cache নিজেও সমস্যা তৈরি করে।

### 🔴 বিপদ ১ — মুছে ফেলা নোট এখনো দেখাচ্ছে

একজন user একটা ভুল নোট মুছে ফেললো। কিন্তু হোমপেজে সেটা তখনো ঝকঝক করছে। ক্লিক করলে 404।

**কারণ:** ডাটাবেস থেকে গেছে, কিন্তু কৌটায় এখনো আছে।

**সমাধান:** যখনই কেউ নোট বদলায় বা মোছে, সাথে সাথে ওই cache key-টা **উড়িয়ে দাও**।

```javascript
async function deleteNote(id) {
  await db.deleteNote(id);
  await redis.del('popular:weekly');    // কৌটাটা খালি করে দাও
}
```

**একটা সূক্ষ্ম কিন্তু জরুরি প্রশ্ন:** নতুন মান বসিয়ে দিলে হয় না? কেন মুছতে হবে?

Boltu ভাই বললো — "দুটো request একসাথে cache-এ লিখতে গেলে কোনটা শেষে বসবে তার কোনো নিশ্চয়তা নেই। একটা পুরনো মান শেষে বসে গেলে সেটা TTL শেষ না হওয়া পর্যন্ত আটকে থাকবে। কিন্তু **মুছে দিলে** পরের যে কেউ পড়তে এলে সে নিজেই ডাটাবেস থেকে সঠিকটা এনে বসাবে।

**Delete is safer than update.**"

### 🔴 বিপদ ২ — রাত ১২টার ধস

এক রাতে ঠিক ১২টা বেজে ০০ সেকেন্ডে ডাটাবেস আবার মরে গেলো।

তানহা log ঘেঁটে বুঝলো —

```
১১:৫০:০০  cache তৈরি হলো, ১০ মিনিটের মেয়াদ
১২:০০:০০  মেয়াদ শেষ, cache উধাও
১২:০০:০০  ঠিক সেই মুহূর্তে ৪,৮০০ জন হোমপেজে
১২:০০:০০  ৪,৮০০ জনই cache miss পেলো
১২:০০:০০  ৪,৮০০টা ভারী query একসাথে ডাটাবেসে 💥
```

এর নাম **Cache Stampede** (বা Thundering Herd) — পালের সব গরু একসাথে দৌড়ে আসা।

**সমাধান — সবার মেয়াদ একসাথে শেষ হতে দিও না:**

```javascript
const ttl = 600 + Math.floor(Math.random() * 120);   // ৬০০-৭২০ সেকেন্ড
await redis.setex(key, ttl, value);
```

এই এলোমেলো অতিরিক্ত সময়টার নাম **Jitter**। এতে সবাই আলাদা আলাদা সময়ে মেয়াদ শেষ করে, তাই ধাক্কাটা ছড়িয়ে যায়।

আরো নিরাপদ চাইলে — একটা lock ব্যবহার করা যায়, যাতে প্রথম request ডাটাবেসে যায় আর বাকিরা অপেক্ষা করে বা পুরনো মানটাই পায়।

### 🔴 বিপদ ৩ — যা নেই তা বারবার খোঁজা

একদিন তানহা দেখলো ডাটাবেসে অদ্ভুত traffic। কেউ একজন পরপর হাজার হাজার এলোমেলো id চাইছে:

```
/notes/99999991  →  cache-এ নেই  →  DB-তে নেই  →  404
/notes/99999992  →  cache-এ নেই  →  DB-তে নেই  →  404
/notes/99999993  →  ...
```

**সমস্যাটা ধরতে পারছো?** যেহেতু কিছু পাওয়াই যাচ্ছে না, তাই cache-এ কিছু জমাও হচ্ছে না। প্রতিটা request সরাসরি ডাটাবেসে যাচ্ছে।

এর নাম **Cache Penetration** — cache-টাকে ফুঁড়ে সোজা ডাটাবেসে চলে যাওয়া।

**সমাধান — "নেই" এটাও একটা উত্তর, এটাও জমা রাখো:**

```javascript
const note = await db.getNote(id);
if (!note) {
  await redis.setex(`note:${id}`, 60, 'NOT_FOUND');   // ১ মিনিট
  return null;
}
```

এখন ওই ভুয়া id গুলো দ্বিতীয়বার থেকে আর ডাটাবেস পর্যন্ত পৌঁছাবেই না।

## যে ভুলটা তানহা উৎসাহে করেছিল

Cache-এর জাদু দেখে তানহা মেতে উঠলো। সে **সবকিছু** cache করা শুরু করলো — প্রতিটা query, প্রতিটা user profile, প্রতিটা search-এর ফলাফল।

দুই সপ্তাহ পর Redis-এর memory ভরে গেলো। আর তখন Redis পুরনো জিনিস বের করে দিতে শুরু করলো জায়গা বানাতে।

**কিন্তু সে ভুল জিনিসগুলো বের করে দিচ্ছিল।**

```
"সপ্তাহের জনপ্রিয় নোট"  →  বের হয়ে গেছে  😱  (সবচেয়ে দরকারি!)
"user 84721 এর ২০২১ সালের search"  →  এখনো আছে  (কেউ কোনোদিন চাইবে না)
```

হিসাব করে দেখা গেলো — তার cache-এর ৭০% জায়গা দখল করে আছে এমন সব জিনিস যেগুলো **কেউ দ্বিতীয়বার চায়নি**।

### Eviction — কাকে বের করবে

জায়গা শেষ হলে কাকে বাদ দেবে, সেটার নিয়ম ঠিক করতে হয়:

| নিয়ম | কী করে | সমস্যা |
|---|---|---|
| **LRU** | যেটা সবচেয়ে অনেকক্ষণ আগে ব্যবহার হয়েছে, সেটা বাদ | — (বেশিরভাগ ক্ষেত্রে সেরা) |
| **LFU** | যেটা সবচেয়ে কম বার ব্যবহার হয়েছে, সেটা বাদ | পুরনো জনপ্রিয় জিনিস আটকে থাকে |
| **FIFO** | যেটা আগে ঢুকেছে সেটা আগে বাদ | জনপ্রিয় জিনিসও বাদ পড়ে যায় |

তানহা Redis-এ সেট করলো:

```
maxmemory-policy allkeys-lru
```

আর তার চেয়েও গুরুত্বপূর্ণ — সে **কম দরকারি জিনিসগুলো cache করা বন্ধ করলো**।

> **Boltu ভাইয়ের নিয়ম:** *"যা **বারবার** পড়া হয় আর **কম** বদলায় — শুধু সেটাই cache কর। বাকিটা memory-র অপচয়, আর অপচয় মানে দরকারি জিনিসের জায়গা কেড়ে নেওয়া।"*

## কতক্ষণ রাখবে — TTL-এর হিসাব

তানহা প্রতিটা জিনিসের জন্য আলাদা সময় ঠিক করলো, আর যুক্তিটা সরল — **কতটা পুরনো তথ্য দেখালে ক্ষতি হবে?**

| জিনিস | TTL | যুক্তি |
|---|---|---|
| জনপ্রিয় নোটের তালিকা | ১০ মিনিট | ১০ মিনিট পুরনো হলে কারো কিছু যায় আসে না |
| একটা নোটের বিস্তারিত | ১ ঘণ্টা | খুব কমই বদলায় |
| User-এর নিজের প্রোফাইল | ৫ মিনিট | নিজে বদলালে দ্রুত দেখতে চায় |
| বিভাগের তালিকা | ২৪ ঘণ্টা | বছরে একবার বদলায় |
| Download সংখ্যা | ৩০ সেকেন্ড | সংখ্যাটা একটু পিছিয়ে থাকলেও চলে |

লক্ষ্য করো — কোনো নিয়ম মুখস্থ করার ব্যাপার নেই। প্রতিটাতেই একটাই প্রশ্ন: **কতক্ষণ পুরনো তথ্য সহ্য করা যাবে?**

---

## Cache কোথায় কোথায় থাকে

তানহা শেষে বুঝলো — Redis একমাত্র cache না। তার সিস্টেমে আসলে **অনেক স্তরে** cache আছে:

```
১. ব্রাউজারের cache        ← user-এর কম্পিউটারেই (কোনো network call নেই)
        ↓
২. CDN edge cache          ← অধ্যায় ৫
        ↓
৩. অ্যাপের নিজের memory     ← সবচেয়ে দ্রুত, কিন্তু প্রতি সার্ভারে আলাদা
        ↓
৪. Redis                   ← সব সার্ভার একই জিনিস দেখে ⭐
        ↓
৫. ডাটাবেসের নিজের cache
        ↓
৬. ডিস্ক                    ← সবচেয়ে ধীর
```

উপরের স্তরে যত কাজ শেষ হবে, তত ভালো।

---

## তানহা যা শিখলো

**১. অন্ধভাবে সার্ভার বাড়ানোর আগে মাপো।** ৯২% সময় একটামাত্র query খাচ্ছিল — এটা না মাপলে কোনোদিন জানতেই পারতো না।

**২. Cache হলো সবচেয়ে সস্তা জাদু।** চার লাইনে ৯৪০ ms → ৬১ ms।

**৩. Cache invalidate করার সময় update না করে delete করো।**

**৪. তিনটা বিপদ মনে রাখো** — Stampede (একসাথে মেয়াদ শেষ), Penetration (যা নেই তা খোঁজা), আর memory ভরে গিয়ে দরকারি জিনিস বেরিয়ে যাওয়া।

**৫. সব cache করো না।** যা বারবার লাগে আর কম বদলায় — শুধু সেটাই।

## দুই বছর পর

"পড়ুয়া" এখন অন্য জিনিস।

```
User:              ৫০,০০,০০০
নোট:               ২,১০,০০,০০০
দিনে পাতা দেখা:     ৯ কোটি
```

Cache আছে, CDN আছে, load balancer আছে, একাধিক সার্ভার আছে।

তবু একদিন একটা অ্যালার্ট এলো, যেটা তানহা আগে কখনো দেখেনি:

```
⚠️  Database disk usage: 92%
⚠️  Write latency increasing: 340ms (normal: 8ms)
```

Cache দিয়ে **পড়ার** সমস্যা সে মিটিয়েছিল। কিন্তু **লেখা**?

লেখা তো cache করা যায় না। লেখা যেতেই হবে ডাটাবেসে। আর ডাটাবেস তো একটাই।

আর ডিস্ক ভরে গেলে? আরো বড় ডিস্ক? সেটাও তো একটা সময় শেষ হবে।

তানহা বুঝলো — এবার তাকে এমন কিছু করতে হবে যেটা সে এতদিন এড়িয়ে চলেছে।
