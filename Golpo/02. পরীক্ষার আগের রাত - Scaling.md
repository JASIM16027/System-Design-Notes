## রাত ৯টা ১৭ মিনিট

> *"আপু, সাইট খুলছে না।"*

তানহা ভাবলো ওই মেয়েটার ইন্টারনেটে সমস্যা। উত্তর দিলো — "একটু পরে চেষ্টা করো।"

**৯টা ১৯ মিনিট:**
> *"লোডিং ঘুরতেই আছে ২ মিনিট ধরে"*

**৯টা ২১ মিনিট:**
> *"503 Service Unavailable দেখাচ্ছে"*

**৯টা ২২ মিনিট:** পরপর সাতটা মেসেজ।

তানহার হাত ঠান্ডা হয়ে গেলো। সে ল্যাপটপ টেনে নিয়ে সার্ভারে ঢুকলো।

```
$ top

CPU:  99.8%
RAM:  3.9 GB / 4.0 GB
Load average: 47.2
```

সার্ভারটা কার্যত অজ্ঞান হয়ে পড়ে আছে।

তানহা analytics খুললো। গত এক ঘণ্টায় **১৪ হাজার visitor**।

কারণটা খুঁজে পেতে বেশিক্ষণ লাগলো না — কেউ একজন ৮০ হাজার সদস্যের একটা ফেসবুক গ্রুপে "পড়ুয়া"-র লিংক দিয়েছে, ক্যাপশন লিখেছে *"এইখানে সব নোট পাওয়া যায়"*।

আর সেদিনই সেমিস্টার ফাইনালের আগের রাত।

তানহা যা কখনো ভাবেনি, তাই হলো — **সাফল্যই তার সিস্টেমকে মেরে ফেললো।**

## প্রথম প্রতিক্রিয়া — সার্ভারটাকে বড় করে দাও

আতঙ্কে তানহা যা করলো, সেটাই যে কেউ করতো। সে ক্লাউড প্যানেলে গিয়ে সার্ভার upgrade বাটনে চাপ দিলো।

```
আগে:  ২ CPU · ৪ GB RAM   →  মাসে ৫০০ টাকা
এখন:  ৮ CPU · ৩২ GB RAM  →  মাসে ৪,২০০ টাকা
```

কয়েক মিনিটের restart। তারপর —

সাইট আবার চললো। ৯টা ৩৮ মিনিটে সব স্বাভাবিক।

তানহা লম্বা একটা নিঃশ্বাস ফেললো।

**যা সে করলো তার নাম Vertical Scaling — মেশিনটাকেই বড় করে ফেলা।**

```
   আগে                         এখন
┌─────────┐              ┌───────────────┐
│ ২ CPU   │     ───►     │    ৮ CPU      │
│ ৪ GB    │              │    ৩২ GB      │
└─────────┘              └───────────────┘
   একই মেশিন, শুধু বেশি শক্তি
```

### Vertical Scaling-এর সুবিধা

- **কোডের একটা লাইনও বদলাতে হয় না।** এটা বিরাট ব্যাপার। মাঝরাতে আতঙ্কের মধ্যে তুমি কোড লিখতে চাও না।
- **১৫ মিনিটে সমাধান।** সবচেয়ে দ্রুত রাস্তা।
- **কোনো জটিলতা নেই।** কোনো load balancer নেই, কোনো session-এর সমস্যা নেই, data একটাই জায়গায়।
- **Debug করা সহজ** — এখনো একটাই মেশিন, একটাই log ফাইল।

তাই কেউ যদি তোমাকে বলে "vertical scaling খারাপ" — সে ভুল বলছে। **প্রথম সমস্যায় vertical scaling-ই সঠিক উত্তর।**

কিন্তু...

## তিনটা দেয়াল

পরের তিন মাসে তানহা পরপর তিনটা দেয়ালে ধাক্কা খেলো।

### দেয়াল ১ — দাম

User আরো বাড়লো। তানহা আবার upgrade করতে গিয়ে দামের তালিকাটা দেখলো:

| Configuration | মাসিক খরচ | আগেরটার তুলনায় |
|---|---|---|
| ২ CPU · ৪ GB | ৫০০ টাকা | — |
| ৮ CPU · ৩২ GB | ৪,২০০ টাকা | ক্ষমতা ৪×, দাম **৮×** |
| ৩২ CPU · ১২৮ GB | ২৮,০০০ টাকা | ক্ষমতা ৪×, দাম **৬.৭×** |
| ৬৪ CPU · ২৫৬ GB | ৯২,০০০ টাকা | ক্ষমতা ২×, দাম **৩.৩×** |

লক্ষ্য করো ব্যাপারটা।

**ক্ষমতা বাড়ে যোগ করে, দাম বাড়ে গুণ করে।**

দ্বিগুণ শক্তিশালী মেশিনের দাম দ্বিগুণ না — তিন থেকে চার গুণ। কারণ বড় হার্ডওয়্যার বানানো কঠিন, আর যত উপরে যাবে তত বিরল।

### দেয়াল ২ — সিলিং

তানহা একদিন সবচেয়ে বড় সার্ভারের তালিকাটা দেখলো। ১২৮ CPU, ২ TB RAM। দাম আকাশছোঁয়া, কিন্তু আছে।

তারপর?

**তারপর আর কিছু নেই।**

পৃথিবীর সবচেয়ে বড় সার্ভারটাও একটা জায়গায় গিয়ে থামে। তুমি চাইলেই অসীম RAM লাগাতে পারবে না। Google, Facebook — এরা যদি vertical scaling-এর উপর নির্ভর করতো, তাহলে দশ বছর আগেই থেমে যেতো।

### দেয়াল ৩ — আর এটাই সবচেয়ে ভয়ংকর

এক শুক্রবার দুপুরে তানহার সার্ভারের ক্লাউড provider একটা রক্ষণাবেক্ষণ চালালো। সার্ভারটা reboot নিলো।

**৪০ মিনিট "পড়ুয়া" পৃথিবী থেকে উধাও ছিল।**

কোনো error page না, কোনো "আমরা ফিরে আসছি" বার্তা না। শুধু কিছুই নেই।

তানহা সেদিন প্রথম শব্দটা শিখলো — **Single Point of Failure**।

> একটামাত্র জিনিস, যেটা মরলে **সবকিছু** মরে।

সে যত বড় সার্ভারই কিনুক না কেন, এই সমস্যাটা যাবে না। বরং যত বড় সার্ভার, তত বেশি ডিম এক ঝুড়িতে।

তানহা Boltu ভাইকে ফোন করলো।

কিন্তু একজন মানুষের একটা সীমা আছে। তার দুটো হাত। সে যত ভালো যন্ত্রই পাক, একসাথে দশটা রান্না করতে পারবে না।

তোর দরকার আরো ভালো ছুরি না। **তোর দরকার আরেকজন রাঁধুনি।**"

## Horizontal Scaling — মেশিন বাড়াও

```
Vertical Scaling (Scale Up)        Horizontal Scaling (Scale Out)

    ┌──────────┐                   ┌────┐  ┌────┐  ┌────┐
    │          │                   │    │  │    │  │    │
    │  বড়      │                   │ ছোট │  │ ছোট │  │ ছোট │
    │  মেশিন   │                   │    │  │    │  │    │
    │          │                   └────┘  └────┘  └────┘
    └──────────┘
   একটা, শক্তিশালী                  অনেকগুলো, সাধারণ
```

তানহা তিনটা সাধারণ সার্ভার চালু করলো। একই কোড, তিন জায়গায় চলছে।

তিনটা ছোট সার্ভারের মোট খরচ একটা বড় সার্ভারের চেয়ে **কম**, অথচ ক্ষমতা বেশি। আর একটা মরে গেলেও বাকি দুটো কাজ করে যাবে।

তানহা খুশি মনে deploy করলো।

**আর সাথে সাথে সব ভেঙে পড়লো।**

## যে সমস্যাটা কেউ আগে থেকে বলে না

user-দের অভিযোগ আসতে শুরু করলো —

> *"লগইন করি, তারপর পরের পাতায় গেলেই আবার লগইন চায়!"*
> *"আপলোড শুরু করলাম, মাঝপথে বললো আপনি লগইন করা নেই"*

তানহা নিজে চেষ্টা করলো। সত্যিই — login করার পর দ্বিতীয় ক্লিকেই সে logout হয়ে যাচ্ছে। আবার কখনো কখনো ঠিক থাকছে। **এলোমেলো।**

কারণটা এখানে:

```
১. User login করলো
   → Load balancer তাকে পাঠালো Server-1 এ
   → Server-1 তার session নিজের memory-তে লিখে রাখলো ✅

২. User পরের পাতায় ক্লিক করলো
   → এবার request গেলো Server-2 তে
   → Server-2 নিজের memory ঘেঁটে দেখলো... কিছু নেই
   → "আপনি কে? লগইন করুন" ❌

৩. পরের ক্লিক গেলো Server-1 এ
   → "ও আচ্ছা, আপনি তো লগইন করাই আছেন" ✅

   একবার হ্যাঁ, একবার না — user পাগল হয়ে যাবে।
```

Boltu ভাই এটা শুনে বললো —

> **"এইটাই horizontal scaling-এর একমাত্র শর্ত, আর একমাত্র কঠিন অংশ। তোকে সার্ভারকে ভুলে যেতে শেখাতে হবে।"**

## Stateless মানে কী

**Stateful সার্ভার** = সার্ভার নিজের কাছে user-এর তথ্য জমা রাখে।
**Stateless সার্ভার** = সার্ভার কিচ্ছু মনে রাখে না; প্রতিটা request নিজেই সব তথ্য বহন করে।

কেন stateless-ই একমাত্র পথ, সেটা দেখো:

| পরিস্থিতি | Stateful | Stateless |
|---|---|---|
| যেকোনো সার্ভার request নিতে পারে? | ❌ না | ✅ হ্যাঁ |
| একটা সার্ভার মরলে? | ওই সার্ভারের সব user-এর session শেষ | কিছুই হয় না |
| নতুন সার্ভার যোগ করলে? | খালি বসে থাকে | সাথে সাথে কাজ শুরু |
| Deploy করতে গেলে? | সবাই logout হয়ে যায় | কেউ টেরও পায় না |

### তিনটা সমাধান, আর কোনটা কেন

**সমাধান ১ — Sticky Session (খারাপ)**

Load balancer-কে বলে দাও — যে user যে সার্ভারে গিয়েছিল, তাকে সবসময় সেখানেই পাঠাও।

*সমস্যা:* ওই সার্ভার মরলে ওর সব user-এর session হারায়। আর load সমানভাবে ভাগ হয় না — নতুন সার্ভার যোগ করলে সে খালি বসে থাকে, কারণ পুরনো user-রা তাদের আগের সার্ভারেই আটকে।

এটা সমাধান না, এটা সমস্যাটাকে গালিচার নিচে ঠেলে দেওয়া।

**সমাধান ২ — Session বাইরে রাখো (ভালো)**

Session সার্ভারের memory-তে না রেখে একটা আলাদা জায়গায় রাখো — যেমন Redis-এ। তাহলে সব সার্ভার একই জায়গা থেকে পড়তে পারে।

```
Server-1 ─┐
Server-2 ─┼──► Redis (সব session এখানে)
Server-3 ─┘
```

*সুবিধা:* সার্ভারগুলো stateless হয়ে গেলো।
*দাম:* প্রতিটা request-এ একটা বাড়তি network call।

**সমাধান ৩ — JWT (তানহা এটাই নিলো)**

Session কোথাও **রাখোই না**। User-এর তথ্যটা একটা signed token-এর ভিতরেই পাঠিয়ে দাও।

```
Token-এর ভিতরে:  { user_id: 4521, name: "তানহা", exp: ... }
                  + একটা signature (যা প্রমাণ করে টোকেনটা জাল না)
```

সার্ভার শুধু signature যাচাই করে — কোনো database, কোনো Redis, কোনো memory লাগে না।

তানহা JWT নিলো, কারণ তার তখন Redis-ও ছিল না, আর এটাই সবচেয়ে সহজে সব সার্ভারে কাজ করে।

## আরো একটা জিনিস তানহা ভুলে গিয়েছিল

Session ঠিক হলো। কিন্তু পরদিন নতুন অভিযোগ —

> *"আমি যে PDF-টা কালকে আপলোড করলাম, সেটা মাঝে মাঝে খুঁজে পাওয়া যায়, মাঝে মাঝে 404 দেখায়!"*

তানহার মাথায় হাত।

সে ভুলে গিয়েছিল — **ফাইলগুলোও তো সার্ভারের ভিতরের ফোল্ডারে!**

```
User আপলোড করলো → Server-1 এর /uploads ফোল্ডারে গেলো
User পরে ডাউনলোড চাইলো → request গেলো Server-2 তে
Server-2 তার নিজের /uploads ঘেঁটে দেখলো → ফাইল নেই → 404
```

Session-এর মতোই একই সমস্যা, শুধু এবার ফাইল নিয়ে।

**সমাধান:** ফাইলও সার্ভারের বাইরে সরাও — object storage-এ (S3, Cloudflare R2, বা যেকোনো ক্লাউড storage)। সব সার্ভার একই জায়গা থেকে পড়ুক-লিখুক।

> **সাধারণ নিয়মটা এই:** সার্ভারের ভিতরে **কোনো কিছুই** স্থায়ীভাবে রাখা যাবে না — session না, ফাইল না, cache না, কিছু না। সার্ভার হবে **নিষ্ক্রিয় আর ভুলোমনা**, যাকে যেকোনো সময় মেরে ফেলে নতুন একটা বসিয়ে দেওয়া যায়।

## দুটোর তুলনা — এক নজরে

| বিষয় | Vertical (Scale Up) | Horizontal (Scale Out) |
|---|---|---|
| কী করা হয় | একই মেশিন শক্তিশালী করা | আরো মেশিন যোগ করা |
| সীমা | হার্ডওয়্যারের সিলিং আছে | কার্যত অসীম |
| খরচ | গুণিতক হারে বাড়ে | রৈখিক হারে বাড়ে |
| একটা মরলে | সব বন্ধ | বাকিরা চলে |
| Upgrade-এ downtime | লাগে | লাগে না |
| জটিলতা | নেই বললেই চলে | অনেক বেশি |
| কোড বদলাতে হয়? | না | হ্যাঁ (stateless বানাতে হয়) |
| কখন | প্রথম সমস্যায়, ছোট দলে | যখন দেয়ালে ধাক্কা খেয়েছো |

---

## তানহা যা শিখলো

**১. প্রথমে vertical, তারপর horizontal।** Vertical scaling লজ্জার কিছু না — এটা দ্রুত, সহজ, আর প্রথম কয়েকটা সমস্যা এভাবেই মেটে।

**২. কিন্তু vertical-এর তিনটা দেয়াল আছে** — দাম গুণিতক হারে বাড়ে, একটা সিলিং আছে, আর সবচেয়ে বড় কথা, single point of failure থেকেই যায়।

**৩. Horizontal scaling-এর একটাই শর্ত — stateless হও।** সার্ভারের ভিতরে session, ফাইল, বা কোনো স্থায়ী জিনিস রাখা যাবে না।

**৪. Peak traffic গড়ের ১০ গুণও হতে পারে।** গড় দিয়ে design করলে peak-এ মরবে।

## কিন্তু একটা প্রশ্ন রয়ে গেলো

তিনটা সার্ভার তো হলো। সবগুলো stateless-ও হলো।

কিন্তু user জানবে কী করে **কোন সার্ভারে** যেতে হবে?

তানহা প্রথমে একটা কাজ করেছিল যেটার কথা মনে পড়লে সে আজও লজ্জা পায় —

সে তিনটা আলাদা ঠিকানা বানিয়ে ফেসবুকে পোস্ট দিয়েছিল:

> *"সাইট slow হলে poruya2.com বা poruya3.com এ চেষ্টা করুন!"*
