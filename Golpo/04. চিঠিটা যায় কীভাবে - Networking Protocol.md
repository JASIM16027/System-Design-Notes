## যে bug তিন দিনেও ধরা গেলো না

> *"বড় PDF গুলো ৬০-৭০% পর্যন্ত নেমে থেমে যায়।"*

তানহা তিন দিন ধরে খুঁজছে।

সার্ভারের log পরিষ্কার — কোনো error নেই। ফাইল ঠিক আছে, নিজে ডাউনলোড করে দেখেছে। ডিস্কে জায়গা আছে। Memory ঠিক আছে।

তবু user-দের কাছে ফাইল অর্ধেক নেমে থামছে।

Boltu ভাই ফোনে বললো — "তোকে একটা প্রশ্ন করি। তুই ব্রাউজারে `poruya.com` লিখলি। এন্টার চাপলি। এরপর **ঠিক কী কী ঘটে** — শুরু থেকে শেষ পর্যন্ত বল তো?"

তানহা বললো — "request যায়, response আসে।"

"সেটা তো ফলাফল। আমি প্রক্রিয়া জিজ্ঞেস করছি। **তুই যে জিনিসটা চালাচ্ছিস, সেটার নিচে কী আছে তুই জানিস না — আর তাই bug টাও খুঁজে পাচ্ছিস না।**"

সেই রাতে Boltu ভাই তাকে একটা কাগজে পুরো ব্যাপারটা এঁকে দিলো।

## ধাপ ১ — ঠিকানা খোঁজা (DNS)

তুমি লিখলে `poruya.com`। কিন্তু ইন্টারনেট **নাম বোঝে না**। ইন্টারনেট বোঝে সংখ্যা — যেমন `103.21.58.12`।

তাহলে নাম থেকে সংখ্যা বের করবে কে? **DNS।**

Boltu ভাইয়ের উদাহরণ: "ধর তুই একজনের নাম জানিস, ফোন নম্বর জানিস না। তুই কী করবি? আগে নিজের ফোনের কন্টাক্ট দেখবি। না পেলে বন্ধুকে জিজ্ঞেস করবি। সে না জানলে সে আরেকজনকে জিজ্ঞেস করবে। DNS ঠিক এই কাজটাই করে, কয়েক মিলিসেকেন্ডে।"

```
১. ব্রাউজারের নিজের মেমোরি   → "আগে কি দেখেছি?" → নেই
২. কম্পিউটারের মেমোরি         → নেই
৩. ISP-র DNS সার্ভার          → নেই, তাহলে খুঁজতে বেরোই

        ↓ এবার আসল খোঁজ শুরু

৪. Root সার্ভার
   "poruya.com চাই"
   → "আমি জানি না, তবে '.com' এর দায়িত্ব যার, তার ঠিকানা এই নাও"

৫. TLD (.com) সার্ভার
   → "poruya.com এর দায়িত্ব যার, তার ঠিকানা এই নাও"

৬. Authoritative সার্ভার
   → "হ্যাঁ, poruya.com মানে 103.21.58.12" ✅
```

**একটা গুরুত্বপূর্ণ ব্যাপার:** এই পুরো যাত্রাটা প্রতিবার হয় না। প্রতিটা ধাপে উত্তরটা কিছুক্ষণের জন্য জমা রাখা হয় (TTL অনুযায়ী)। তাই দ্বিতীয়বার থেকে উত্তরটা সাথে সাথেই পাওয়া যায়।

**আর একটা কাজের জিনিস:** DNS নিজেই একটা মোটা দাগের load balancer হতে পারে — একই নামের বিপরীতে একাধিক IP দেওয়া যায়, আর user-এর অবস্থান দেখে কাছেরটা দেওয়া যায়। এই কৌশলটা পরের অধ্যায়ে (CDN) কাজে লাগবে।

## ধাপ ২ — হাত মেলানো (TCP Handshake)

ঠিকানা পাওয়া গেলো। এবার কি সরাসরি data পাঠানো যাবে?

না। আগে **পরিচয় ও সম্মতি**।

```
User    → "শুনতে পাচ্ছো? আমি কথা বলতে চাই"        (SYN)
Server  → "পাচ্ছি। তুমিও কি আমাকে পাচ্ছো?"         (SYN-ACK)
User    → "হ্যাঁ পাচ্ছি"                            (ACK)

        → এবার সংযোগ প্রস্তুত, data পাঠানো যাবে
```

এই তিন ধাপের নাম **Three-way Handshake**।

Boltu ভাই বললো — "ফোনে কথা বলার আগে যেমন 'হ্যালো... হ্যালো... হ্যাঁ শুনতে পাচ্ছি' — ঠিক তাই।"

**এখানে একটা খরচ লুকানো আছে:** এই হাত মেলানোতেই একটা পুরো round trip সময় চলে যায়। ঢাকা থেকে সিঙ্গাপুরে যদি এক দিকে যেতে ৪০ms লাগে, তাহলে শুধু হাত মেলাতেই ৮০ms। **কোনো data পাঠানোর আগেই।**

এই কারণেই connection বারবার না খুলে **একটা connection বারবার ব্যবহার করা** (keep-alive) এত গুরুত্বপূর্ণ।

### TCP কেন, UDP কেন না?

তানহার PDF-এর জন্য TCP-ই লাগবে। কারণ TCP তিনটা প্রতিশ্রুতি দেয়:

| TCP যা করে | কেন গুরুত্বপূর্ণ |
|---|---|
| প্রতিটা টুকরো পৌঁছেছে কিনা নিশ্চিত করে | PDF-এর এক টুকরো হারালে ফাইল নষ্ট |
| হারিয়ে গেলে আবার পাঠায় | নেট একটু খারাপ হলেও ফাইল ঠিক নামবে |
| ক্রম ঠিক রাখে | ৫ নম্বর টুকরো ৩ নম্বরের আগে বসলে ফাইল ভাঙা |

**তাহলে UDP কোথায় লাগে?** যেখানে দ্রুততা নির্ভুলতার চেয়ে জরুরি।

ভিডিও কলে একটা frame হারালে কেউ টেরও পায় না। কিন্তু TCP যদি সেই হারানো frame-টার জন্য অপেক্ষা করে আর আবার পাঠায়, তাহলে পুরো কলটা আধ সেকেন্ড পিছিয়ে যাবে — **সেটা সবাই টের পাবে**।

তাই ভিডিও কল, লাইভ স্ট্রিমিং, অনলাইন গেম — এসবে UDP।

> **এক লাইনে:** *TCP = "সব পৌঁছাতেই হবে।" UDP = "যা যাচ্ছে যাক, দেরি করা যাবে না।"*

## ধাপ ৩ — তালা লাগানো (TLS / HTTPS)

তানহার সাইটে login আছে, মানে password যায়।

খোলা অবস্থায় পাঠালে? মাঝখানের যে কেউ — ক্যাফের ওয়াইফাই-এর মালিক, ISP, বা কোনো আক্রমণকারী — সব পড়ে ফেলতে পারবে।

তাই TCP handshake-এর পর আরেকটা handshake হয়:

```
১. Client:  "আমি এই এই পদ্ধতিতে কথা বলতে পারি"

২. Server:  "ঠিক আছে, এই পদ্ধতিটা নিই। আর এই নাও আমার সার্টিফিকেট —
             একটা বিশ্বস্ত কর্তৃপক্ষ সই করে বলেছে আমি সত্যিই poruya.com"

৩. Client:  সার্টিফিকেটটা যাচাই করে
             → জাল হলে ব্রাউজার লাল সতর্কবার্তা দেখাবে
             → ঠিক থাকলে দুই পক্ষ মিলে একটা গোপন চাবি বানায়

৪. এরপর থেকে সব কথা ওই চাবি দিয়ে তালাবদ্ধ 🔒
```

**তিনটা জিনিস একসাথে নিশ্চিত হয়:**
- **গোপনীয়তা** — মাঝখানের কেউ পড়তে পারবে না
- **অখণ্ডতা** — কেউ মাঝপথে বদলে দিতে পারবে না
- **পরিচয়** — সার্ভারটা সত্যিই যাকে দাবি করছে, সে-ই

`http` আর `https` — এই একটা অক্ষরের পুরো মানে এটাই।

## ধাপ ৪ — এবার আসল কথা (HTTP)

সংযোগ হলো, তালাও লাগলো। এবার আসল অনুরোধ:

```
GET /notes/physics-101.pdf HTTP/1.1
Host: poruya.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Accept: application/pdf
```

আর সার্ভারের উত্তর:

```
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Length: 8388608
Accept-Ranges: bytes

[...ফাইলের byte গুলো...]
```

## 🎯 আর এখানেই তানহা তার bug-টা খুঁজে পেলো

Boltu ভাই আঙুল দিয়ে দেখালো —

> *"তোর response-এ `Content-Length` নেই। ব্রাউজার জানেই না ফাইলটা কত বড়।"*

তানহা ফাইলটা stream করে পাঠাচ্ছিল, কিন্তু আকারটা বলে দিচ্ছিল না।

ফলে যা হচ্ছিল —

```
ব্রাউজার:  "ডাউনলোড শুরু করলাম... কত বড় জানি না...
            ২ সেকেন্ড কোনো data আসছে না...
            মনে হয় শেষ। বন্ধ করে দিই।" ❌

আসলে:     ফাইলটা তখনো ৩০% বাকি ছিল, শুধু নেটওয়ার্ক একটু ধীর ছিল
```

ছোট ফাইলগুলো এক নিঃশ্বাসে চলে যেতো, তাই সমস্যা হতো না। বড় ফাইলে মাঝখানে একটু বিরতি পড়লেই ব্রাউজার ধরে নিতো শেষ হয়ে গেছে।

**সমাধান তিন লাইনের:**

```javascript
res.setHeader('Content-Length', fileSize);        // কত বড়, সেটা বলো
res.setHeader('Accept-Ranges', 'bytes');          // থেমে গেলে যেন আবার
                                                   // ওখান থেকেই শুরু করা যায়
res.setHeader('Content-Type', 'application/pdf');
```

`Accept-Ranges` যোগ করায় বোনাস পাওয়া গেলো — এখন ডাউনলোড মাঝপথে থেমে গেলে **যেখানে থেমেছিল সেখান থেকেই আবার শুরু** হয়, শূন্য থেকে না।

তিন দিনের bug, তিন লাইনে শেষ।

> **তানহার উপলব্ধি:** *"আমি অ্যাপ্লিকেশন লেভেলে bug খুঁজছিলাম, কিন্তু bug টা ছিল protocol লেভেলে। নিচের স্তরটা না জানলে উপরের স্তরের অর্ধেক সমস্যা কখনোই বুঝতে পারবে না।"*

## HTTP-রও বয়স বেড়েছে

Bug ঠিক হওয়ার পর তানহা খেয়াল করলো — তার হোমপেজ এখনো ধীর।

সে ব্রাউজারের Network tab খুলে গুনলো — **একটা পাতা লোড হতে ৫২টা আলাদা ফাইল** আসছে। CSS, JS, আইকন, ফন্ট, ছবি।

### HTTP/1.1 — এক লেনের রাস্তা

HTTP/1.1-এ একটা connection দিয়ে **একবারে একটা** জিনিস। প্রথমটা শেষ না হলে দ্বিতীয়টা শুরুই হবে না।

```
Connection:  [file-1]───► [file-2]───► [file-3]───► ...

    file-1 ধীর হলে পিছনের সবাই দাঁড়িয়ে থাকে
```

এটাকে বলে **Head-of-Line Blocking** — লাইনের প্রথম লোকটা আটকে গেলে পুরো লাইন আটকে যায়।

ব্রাউজার এটা এড়াতে ৬টা connection খোলে, কিন্তু ৫২টা ফাইলের জন্য ৬টা লেন যথেষ্ট না। আর প্রতিটা connection-এ আবার আলাদা handshake!

### HTTP/2 — বহু লেনের রাস্তা

HTTP/2 এলো **multiplexing** নিয়ে — একটাই connection, কিন্তু তার ভিতরে অনেকগুলো সমান্তরাল ধারা।

```
              ┌─ file-1 ─┐
Connection ───┼─ file-2 ─┼───►  সব একসাথে
              ├─ file-3 ─┤
              └─ ... ────┘
```

সাথে আরো দুটো জিনিস —
- **Header compression** — প্রতিটা request-এ একই header বারবার না পাঠিয়ে সংক্ষেপে পাঠানো
- **Binary format** — text-এর বদলে binary, যা parse করা দ্রুত

তানহা Nginx-এ শুধু একটা শব্দ যোগ করলো:

```nginx
listen 443 ssl http2;
```

**পাতা লোড হওয়ার সময় ২.৮ সেকেন্ড থেকে নেমে ১.৭ সেকেন্ড।** কোডের একটা লাইনও না বদলে, ৪০% উন্নতি।

### HTTP/3 — রাস্তাটাই বদলে ফেলা

HTTP/2-তেও একটা সমস্যা রয়ে গিয়েছিল। Multiplexing হয়েছে **HTTP স্তরে**, কিন্তু নিচে তো এখনো TCP। আর TCP-র নিয়ম হলো — একটা packet হারালে সে বাকি সব থামিয়ে দিয়ে সেটার জন্য অপেক্ষা করে।

মানে **TCP স্তরে head-of-line blocking রয়ে গেছে**।

HTTP/3 সমাধান করলো সবচেয়ে সাহসী উপায়ে — **TCP-ই বাদ দিয়ে**। এটা চলে QUIC-এর উপর, যা UDP-ভিত্তিক কিন্তু নির্ভরযোগ্যতা নিজে সামলায়।

**লাভগুলো:**
- একটা ধারায় packet হারালে বাকি ধারাগুলো থামে না
- Handshake দ্রুত (TLS আর connection একসাথে, ১ round trip-এ)
- **Connection migration** — মোবাইলে ওয়াইফাই থেকে মোবাইল ডেটায় গেলেও connection টিকে থাকে

মোবাইল user-এর জন্য এই শেষ সুবিধাটা বিশাল — আর "পড়ুয়া"-র ৮০% user মোবাইলে।

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| সাল | ১৯৯৭ | ২০১৫ | ২০২২ |
| নিচে কী | TCP | TCP | **QUIC (UDP)** |
| একসাথে অনেক ফাইল | ❌ | ✅ | ✅ |

| নেটওয়ার্ক বদলালে টেকে | ❌ | ❌ | ✅ |

## পুরো যাত্রাটা এক নজরে

তানহা কাগজটা দেয়ালে টাঙিয়ে রাখলো:

```
   ব্রাউজারে poruya.com লিখে এন্টার
              │
              ▼
   ① DNS: নাম → IP                      (~২০-১০০ms, cache থাকলে ০)
              │
              ▼
   ② TCP: তিন ধাপের হাত মেলানো           (~১ round trip)
              │
              ▼
   ③ TLS: সার্টিফিকেট + গোপন চাবি        (~১-২ round trip)
              │
              ▼
   ④ HTTP: GET /  →  200 OK              (আসল কাজ)
              │
              ▼
   ⑤ HTML পড়ে আরো ৫২টা ফাইলের অনুরোধ
      (HTTP/2 হলে একটা connection-এই সব একসাথে)
              │
              ▼
   ⑥ ব্রাউজার সব সাজিয়ে পাতা দেখায়
```

লক্ষ্য করো — **আসল কাজটা (৪ নম্বর) শুরুই হয় তিন ধাপ প্রস্তুতির পর।** এই কারণেই latency কমানোর সবচেয়ে বড় কৌশল হলো — এই প্রস্তুতিগুলো কমানো বা **দূরত্বটাই কমিয়ে ফেলা**।

## তানহা যা শিখলো

**১. নিচের স্তর না জানলে উপরের অর্ধেক bug কখনোই বোঝা যাবে না।** তার তিন দিনের bug ছিল একটা অনুপস্থিত header।

**২. প্রতিটা ধাপে সময় লাগে।** DNS + TCP + TLS মিলিয়ে আসল data-র আগেই কয়েকশো মিলিসেকেন্ড চলে যেতে পারে।

**৩. TCP নির্ভরযোগ্য, UDP দ্রুত।** ফাইল-তথ্যে TCP, ভিডিও-গেমে UDP।

**৪. HTTP/2 চালু করা কার্যত বিনামূল্যের উন্নতি** — এক লাইনের config।

**৫. Latency-র মূল শত্রু round trip সংখ্যা।** প্রতিটা যাওয়া-আসা সময় খায়।
