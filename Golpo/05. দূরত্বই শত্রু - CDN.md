## যে সমস্যার কোনো দোষী নেই

> *"আপু, আমি কানাডা থেকে ব্যবহার করি। একটা পাতা লোড হতে ৮ সেকেন্ড লাগে। ঢাকার বন্ধুরা বলে ওদের ১ সেকেন্ডে হয়ে যায়।"*

তানহা সব জায়গায় খুঁজলো।

```
CPU:        ১৮%          ✅
RAM:        ৯ GB / ৩২ GB  ✅
DB query:   গড়ে ১২ms      ✅
Error log:  খালি          ✅
```

সার্ভার কোনো অন্যায় করছে না। তবু কানাডার user-এর ৮ সেকেন্ড লাগছে।

তানহা নিজে একটা VPN দিয়ে টরন্টো থেকে সাইটে ঢুকলো।

**সত্যিই ৮ সেকেন্ড।**

সে ব্রাউজারের Network tab খুলে বসে রইলো। আর তখনই ব্যাপারটা চোখে পড়লো।

প্রতিটা ছোট ছোট ফাইল — একটা ২০ KB-র আইকন, একটা ৫ KB-র CSS — প্রত্যেকটার পাশে লেখা:

```
logo.png       ২০ KB    ২৪১ ms
style.css       ৫ KB    ২৩৮ ms
app.js        ১২০ KB    ৩১২ ms
icon-1.svg      ২ KB    ২৩৯ ms
icon-2.svg      ২ KB    ২৪০ ms
...  (আরো ৪৭টা)
```

**২ KB-র একটা আইকন আনতে ২৪০ মিলিসেকেন্ড!**

ফাইলটা ছোট। সার্ভার দ্রুত। তবু ২৪০ ms।

Boltu ভাই ফোনে শুনে বললো — "তুই ভুল জায়গায় খুঁজছিস। **এখানে দোষ কারো না। দোষ দূরত্বের।**"

## আলোর চেয়ে দ্রুত কেউ যেতে পারে না

তানহার সার্ভার সিঙ্গাপুরে। টরন্টো থেকে সিঙ্গাপুর সোজা পথে প্রায় **১৫,০০০ কিলোমিটার**।

Boltu ভাই হিসাবটা করে দেখালো —

```
আলোর গতি (ফাইবার অপটিকে): প্রায় ২,০০,০০০ কিমি/সেকেন্ড

এক দিকে যেতে:   ১৫,০০০ ÷ ২,০০,০০০  =  ০.০৭৫ সেকেন্ড = ৭৫ ms
যাওয়া-আসা:      ১৫০ ms

আর বাস্তবে সোজা পথে যায় না — ঘুরে ঘুরে, রাউটার পেরিয়ে যায়
তাই বাস্তবে:    প্রায় ২৪০ ms
```

> **"এইটা তোর কোডের সমস্যা না। এইটা পদার্থবিজ্ঞান। তুই যত ভালো কোড লিখিস, আলোকে দ্রুত ছোটাতে পারবি না।"**

আর এখানেই আসল বিপদটা:

```
৫২টা ফাইল × ২৪০ ms
```

HTTP/2-র কারণে সব সমান্তরালে যাচ্ছে ঠিকই, কিন্তু তবু —
- আগে DNS: ২৪০ ms
- তারপর TCP handshake: ২৪০ ms
- তারপর TLS handshake: ৪৮০ ms
- তারপর HTML: ২৪০ ms
- HTML পড়ে বাকি ফাইলের অনুরোধ: আরো ২৪০ ms

**কোনো ফাইল বড় না। শুধু প্রতিবার আটলান্টিক পেরোতে হচ্ছে।**

## বইয়ের দোকানের উদাহরণ

Boltu ভাই বললো —

"ধর তোর একটা বইয়ের দোকান আছে, শুধু ঢাকায়। চট্টগ্রামের একজন একটা বই অর্ডার করলো। কুরিয়ারে যেতে **দুই দিন**।

তুই কি কুরিয়ারকে দ্রুত ছুটতে বলবি? তাতে কি ঢাকা-চট্টগ্রামের দূরত্ব কমবে?

না। **তুই চট্টগ্রামে একটা ছোট গুদাম বানাবি।** সেখানে জনপ্রিয় বইগুলো আগে থেকেই রাখবি। এখন চট্টগ্রামের অর্ডার দুই দিনের বদলে **দুই ঘণ্টায়** পৌঁছাবে।

আর এই ছোট গুদামগুলোর নাম — **CDN-এর Edge Server**।"

## CDN আসলে কী

CDN মানে **Content Delivery Network** — পৃথিবীর শত শত শহরে ছড়ানো সার্ভারের একটা জাল, যেখানে তোমার ফাইলগুলোর copy রাখা থাকে।

```
CDN ছাড়া:
   টরন্টোর user ─────── ১৫,০০০ কিমি ────────► সিঙ্গাপুরের সার্ভার
                          (২৪০ ms, প্রতিটা ফাইলের জন্য)

CDN সহ:
   টরন্টোর user ──২০ms──► টরন্টোর Edge Server
                               │
                               └── ফাইল না থাকলে একবার
                                   মূল সার্ভার থেকে এনে
                                   নিজের কাছে রেখে দেয়
```

**প্রথম টরন্টোবাসীর জন্য একটু দেরি হলো** (edge-কে একবার সিঙ্গাপুর যেতে হলো)। কিন্তু তার পরের **সব** টরন্টোবাসীর জন্য — ২০ মিলিসেকেন্ড।

তানহা Cloudflare-এ সাইন আপ করলো (free tier আছে), DNS-টা তাদের দিকে ঘুরিয়ে দিলো।

**পরদিন টরন্টোর সেই ছেলেটা মেসেজ দিলো:**

> *"আপু কী করেছেন! এখন ১ সেকেন্ডেরও কম লাগে 😲"*

## কীভাবে user সবচেয়ে কাছের গুদামটা খুঁজে পায়

তানহার কৌতূহল হলো — CDN কী করে বুঝলো কে টরন্টোতে আর কে ঢাকায়?

দুটো কৌশল।

**১. DNS-ভিত্তিক:** user যখন নাম resolve করে, CDN-এর DNS সার্ভার তার IP দেখে আন্দাজ করে সে কোথাকার, আর সেই অনুযায়ী কাছের edge-এর ঠিকানা দেয়। **একই নাম, ভিন্ন ভিন্ন মানুষের জন্য ভিন্ন IP।**

**২. Anycast:** আরো চমৎকার কৌশল — পৃথিবীর সব edge server **একই IP** ঘোষণা করে। তখন ইন্টারনেটের নিজের রাউটিং ব্যবস্থাই packet-টাকে সবচেয়ে কাছের সার্ভারে পৌঁছে দেয়। কোনো আলাদা হিসাব লাগে না।

তানহা response header দেখে নিজেই যাচাই করলো:

```
cf-cache-status: HIT
cf-ray: 8a3f2c1b4d5e-YYZ        ← YYZ = টরন্টো বিমানবন্দরের কোড!
age: 3421                        ← ৩৪২১ সেকেন্ড ধরে এখানে আছে
```

## কী দেবে, কী দেবে না

তানহা প্রথমে ভেবেছিল সব CDN-এ দিয়ে দেবে। Boltu ভাই থামালো।

### ✅ অবশ্যই দেবে

| জিনিস | কেন |
|---|---|
| ছবি, আইকন, লোগো | সবার জন্য একই, কখনো বদলায় না |
| CSS, JavaScript | সবার জন্য একই |
| ফন্ট | আকারে বড়, সবার জন্য একই |
| **নোটের PDF** | তানহার সবচেয়ে ভারী জিনিস — সবচেয়ে বেশি লাভ এখানেই |

### ❌ কখনোই দেবে না

- User-এর নিজের dashboard
- তার প্রোফাইল, তার আপলোড করা তালিকা
- Login-এর পরের যেকোনো ব্যক্তিগত পাতা

**কেন এত কড়াকড়ি?**

Boltu ভাই একটা ভয়ংকর দৃশ্য আঁকলো —

> "ধর তুই ভুল করে dashboard-টাও cache করে দিলি। এখন তানহা login করে dashboard খুললো, CDN সেটা edge-এ জমা করে রাখলো।
>
> পরের যে কেউ ওই একই URL-এ গেলো — CDN তাকে **তানহার dashboard** দেখিয়ে দিলো।
>
> এটা bug না। **এটা data breach।**"

তানহা সাথে সাথে নিশ্চিত করলো:

```
সবার জন্য একই জিনিস:      Cache-Control: public, max-age=31536000
Login-এর পরের সব কিছু:    Cache-Control: private, no-store
```

## যে ভুলটা তানহা করেছিল

CDN চালু করার এক সপ্তাহ পর সে সাইটের ডিজাইন বদলালো। নতুন CSS deploy করলো।

আর তারপর মাথায় হাত।

**কারো ব্রাউজারে নতুন ডিজাইন আসছে না।** সবাই পুরনোটা দেখছে। সে নিজে incognito-তে খুললো — পুরনোটা। ফোনে — পুরনোটা।

কারণ সে `style.css` এর জন্য **এক বছরের** cache সময় দিয়েছিল। CDN তার কথা অক্ষরে অক্ষরে মানছে — "তুমিই তো বলেছিলে এক বছর রাখতে।"

### সমাধান — নাম বদলে দাও

এখানে একটা চমৎকার কৌশল আছে, যেটা প্রায় সব আধুনিক build tool স্বয়ংক্রিয়ভাবে করে:

```
আগে:  style.css              ← নাম কখনো বদলায় না, তাই cache আটকে থাকে
এখন:  style.a3f8b2c1.css     ← ফাইলের ভিতরের লেখা বদলালে নামও বদলায়
```

কোড বদলালে hash বদলায়, hash বদলালে **নাম বদলায়**, নাম বদলালে **এটা CDN-এর কাছে সম্পূর্ণ নতুন ফাইল**।

```
Deploy করার পর HTML-এ থাকে:
   <link href="/style.9d4e7f2a.css">   ← নতুন নাম

পুরনো style.a3f8b2c1.css এখনো edge-এ পড়ে আছে —
কিন্তু কেউ আর ওটা চাইছেই না। কোনো ক্ষতি নেই।
```

**দুটো বিপরীত জিনিস একসাথে পাওয়া গেলো:**
- ফাইলগুলো চিরকালের জন্য cache-এ (সর্বোচ্চ গতি) ✅
- Deploy করলেই সবাই সাথে সাথে নতুনটা পায় (সর্বোচ্চ তাজা) ✅

**তবে একটা শর্ত:** HTML ফাইলটাতে **ছোট cache সময় বা no-cache** দিতে হবে — কারণ HTML-ই তো নতুন নামগুলো বহন করে। HTML পুরনো হলে সে পুরনো নামই দেখাবে।

```
style.a3f8b2.css   →  max-age=31536000  (এক বছর)
app.9d4e7f.js      →  max-age=31536000  (এক বছর)
index.html         →  no-cache          (প্রতিবার যাচাই করো)
```

### আর জরুরি অবস্থার জন্য — Purge

কোনো ফাইল সত্যিই এখনই সরাতে হলে CDN-এর purge API আছে। তবে সব edge-এ ছড়াতে কয়েক সেকেন্ড থেকে কয়েক মিনিট লাগে, আর বেশি purge করলে খরচও লাগে।

> **নিয়ম:** Versioned নাম হবে তোমার **স্বাভাবিক পদ্ধতি**, purge হবে **জরুরি অবস্থার অস্ত্র**।

## তানহা যে সুবিধাগুলো আশাই করেনি

CDN চালু করার পর তিনটা জিনিস ঘটলো যেগুলোর কথা সে ভাবেওনি।

### ১. সার্ভারের বিল কমে গেলো

```
CDN-এর আগে:   মূল সার্ভারে দিনে ৪.২ কোটি request
CDN-এর পরে:   মূল সার্ভারে দিনে ৬০ লাখ request

৮৬% traffic edge-এই শেষ হয়ে যাচ্ছে
```

তানহা তিনটা সার্ভার থেকে নেমে **দুটোতে** এলো। খরচ কমলো, তবু সাইট আগের চেয়ে দ্রুত।

**কারণ:** ক্লাউড থেকে data বের হওয়ার (egress) খরচ অনেক বেশি, আর CDN-এর সেই খরচ তুলনামূলক কম। ভারী PDF গুলো edge থেকে গেলে বিলে বড় পার্থক্য হয়।

### ২. একটা আক্রমণ সে টেরই পেলো না

এক রাতে কেউ "পড়ুয়া"-তে DDoS আক্রমণ চালালো — সেকেন্ডে লাখ লাখ ভুয়া request।

তানহা পরদিন সকালে Cloudflare-এর dashboard-এ দেখলো:

```
আটকানো হয়েছে:  ৪.১ কোটি request
মূল সার্ভারে পৌঁছেছে:  ০
```

আক্রমণটা পৃথিবীর তিনশো শহরে ছড়িয়ে গিয়ে edge-এই শুষে নেওয়া হয়েছে। তার সার্ভার পর্যন্ত একটা packet-ও পৌঁছায়নি।

**তানহা রাতে দিব্যি ঘুমিয়েছিল, তার কিছুই জানা ছিল না।**

### ৩. ছবিগুলো নিজে থেকেই ছোট হয়ে গেলো

CDN তার JPEG ছবিগুলো স্বয়ংক্রিয়ভাবে WebP-তে রূপান্তর করে দিচ্ছিল যেসব ব্রাউজার সেটা বোঝে তাদের জন্য। সাথে Brotli compression।

**ছবির মোট আকার ৪০% কমে গেলো** — তানহা কিছুই না করে।

---

## Edge Computing — পরের ধাপ

তানহা একদিন পড়লো যে আধুনিক CDN-এ শুধু ফাইল রাখা যায় না, **কোডও চালানো যায়**।

Cloudflare Workers, Lambda@Edge — এগুলো তোমার ছোট ছোট function কে পৃথিবীর তিনশো শহরে চালায়।

তানহা এটা দিয়ে একটা কাজ করলো — user-এর দেশ দেখে ভাষা ঠিক করা:

```
বাংলাদেশ থেকে এলে   → বাংলা ইন্টারফেস
অন্য কোথাও থেকে      → ইংরেজি
```

আগে এই সিদ্ধান্তটা নিতে সিঙ্গাপুর পর্যন্ত যেতে হতো (২৪০ ms)। এখন সেটা user-এর ২০ ms দূরত্বেই হয়ে যায়।

---

## CDN-এর অসুবিধাও আছে

তানহা দুটো ব্যাপারে ধাক্কা খেয়েছিল, তাই সেগুলোও বলা দরকার।

**১. Debug করা কঠিন হয়ে যায়।** কোনো সমস্যা দেখলে এখন প্রশ্ন — এটা কি আমার কোডে, নাকি edge-এর পুরনো copy দেখাচ্ছে? তানহা এক ঘণ্টা নষ্ট করেছিল এমন একটা bug খুঁজে, যেটা আসলে ছিল না — শুধু edge-এ পুরনো ফাইল পড়ে ছিল।

**২. আরেকটা নির্ভরতা।** CDN নিজে down হলে তোমার সাইটও প্রভাবিত হয়। বিরল, কিন্তু হয়।

---

## তানহা যা শিখলো

**১. Latency-র সবচেয়ে বড় উপাদান প্রায়ই দূরত্ব, প্রক্রিয়াকরণ না।** সার্ভার ১২ms-এ কাজ শেষ করছিল, কিন্তু চিঠিটা যেতে-আসতেই ২৪০ ms।

**২. কোড দিয়ে পদার্থবিজ্ঞান হারানো যায় না — জিনিসটাকে কাছে নিয়ে যেতে হয়।**

**৩. Static সব কিছু CDN-এ দাও, ব্যক্তিগত কিছু কখনো না।** ভুল করলে সেটা bug না, data breach।

**৪. Versioned নাম + লম্বা cache** — এটাই সঠিক পদ্ধতি, purge না।

**৫. CDN শুধু গতি না** — খরচ কমায়, DDoS আটকায়, ছবি ছোট করে, HTTPS দেয়।

## কিন্তু একটা জায়গায় CDN কিছুই করতে পারলো না

কয়েক মাস পর সাইট আবার ধীর হতে শুরু করলো।

কিন্তু এবার অদ্ভুত ব্যাপার — **ছবি, CSS, PDF সব বিদ্যুৎগতিতে আসছে** (CDN-এর কল্যাণে)। ধীর হচ্ছে শুধু **হোমপেজটা** — মানে HTML-টা।

কারণ হোমপেজ তো CDN-এ রাখা যায় না, ওটা প্রতিবার সার্ভার থেকে বানাতে হয়।

তানহা সার্ভারে গিয়ে মাপলো — একটা request-এ মোট সময়ের **৯০%** যাচ্ছে একটাই জায়গায়।

ডাটাবেসে।
