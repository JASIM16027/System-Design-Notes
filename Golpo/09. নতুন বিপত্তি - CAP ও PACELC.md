## দুপুর ১টা ৪০ মিনিট

"পড়ুয়া" এখন দুই অঞ্চলে —

```
এশিয়া অঞ্চল (সিঙ্গাপুর)     ← বাংলাদেশ ও আশপাশের user
ইউরোপ অঞ্চল (ফ্রাঙ্কফুর্ট)  ← প্রবাসী শিক্ষার্থীরা

দুই অঞ্চলের data একে অপরের সাথে sync থাকে
```

এক দুপুরে ভারত মহাসাগরের নিচের একটা সাবমেরিন কেবলে সমস্যা হলো।

দুই অঞ্চল **একে অপরের সাথে কথা বলতে পারছে না**।

কিন্তু — এবং এখানেই আসল ব্যাপার — **দুই অঞ্চলের সার্ভারই দিব্যি বেঁচে আছে**। দুই দিকেই user আছে, তারা কাজ করতে চাইছে।

তানহার ফ্রাঙ্কফুর্টের সার্ভারের সামনে এখন একটা প্রশ্ন:

> *একজন user একটা নোট চাইছে। কিন্তু আমি জানি না এশিয়ায় গত কয়েক মিনিটে ওই নোটটা কেউ বদলেছে কিনা বা মুছে দিয়েছে কিনা।*
>
> *আমি কী করবো?*

## দুটো রাস্তা, আর তৃতীয় কোনো রাস্তা নেই

### 🅰️ রাস্তা ১ — সঠিকতা বাঁচাও

> *"আমি নিশ্চিত না আমার কাছের তথ্যটা সর্বশেষ কিনা। ভুল তথ্য দেখানোর চেয়ে কিছু না দেখানো ভালো।"*

```
User → Server:  "নোটটা দেখাও"
Server → User:  "দুঃখিত, সাময়িক সমস্যা। পরে চেষ্টা করুন।"  ❌
```

**Data সঠিক রইলো। কিন্তু সেবা বন্ধ।**

### 🅱️ রাস্তা ২ — সেবা বাঁচাও

> *"আমার কাছে যা আছে তাই দেখাই। লাইন ঠিক হলে মিলিয়ে নেবো।"*

```
User → Server:  "নোটটা দেখাও"
Server → User:  "এই নাও" (হয়তো ৫ মিনিট পুরনো তথ্য)  ✅
```

**সেবা চালু রইলো। কিন্তু তথ্য হয়তো ভুল।**

## CAP Theorem — তিনটার মধ্যে দুটো

Boltu ভাই ব্যাখ্যা করলো —

"যেকোনো distributed system-এ তিনটা জিনিস থাকে:

**C — Consistency:** সব জায়গায় একই তথ্য দেখাবে। তুমি কিছু লিখলে, যেকোনো সার্ভার থেকে পড়লে সেই নতুন জিনিসটাই পাবে।

**A — Availability:** প্রতিটা request একটা উত্তর পাবে। Error না, timeout না — একটা উত্তর।

**P — Partition Tolerance:** সার্ভারগুলোর মাঝে যোগাযোগ বিচ্ছিন্ন হলেও সিস্টেম কাজ করতে থাকবে।

**CAP theorem বলে — এই তিনটার মধ্যে একসাথে সর্বোচ্চ দুটো পাওয়া যায়।**"

```
                    C
                   / \
              CP  /   \  CA
                 /     \
                A ─────  P
                    AP
```

তানহা বললো — "তাহলে আমি C আর A নিই, P বাদ দিই!"

Boltu ভাই হাসলো — "**P তুই বাদ দিতে পারবি না।** P মানে network ভাঙা। তুই কি সমুদ্রের নিচের কেবলকে না ভাঙার নির্দেশ দিতে পারবি?

Network ভাঙবেই। কেবল কাটবে, রাউটার মরবে, ডেটা সেন্টার বিচ্ছিন্ন হবে। এটা তোর হাতে নেই।

তাই **distributed system-এ P বাধ্যতামূলক।** আর তখন আসল প্রশ্নটা দাঁড়ায় —"

> **"Network ভেঙে গেলে তুই কোনটা ছেড়ে দিবি — Consistency নাকি Availability?"**

### তাহলে CA কোথায়?

তানহার প্রশ্ন — "কিন্তু ছবিতে তো CA-ও আছে!"

"CA মানে হলো এমন একটা সিস্টেম যেখানে network ভাঙার সম্ভাবনাই নেই। **সেটা কেবল তখনই সম্ভব যখন সার্ভার একটাই।**

তোর প্রথম দিনের এক-সার্ভারের সিস্টেমটা CA ছিল — ভাগ করার মতো কিছুই ছিল না, তাই partition-ও ছিল না।

কিন্তু যেই তুই দ্বিতীয় সার্ভার যোগ করলি, সেই মুহূর্তে CA মরে গেলো। **Distributed system-এ CA বলে কিছু নেই।**"

## তানহার সিদ্ধান্ত — আর এখানেই আসল শিক্ষা

তানহা প্রথমে ভাবলো পুরো সিস্টেমের জন্য একটা সিদ্ধান্ত নেবে।

Boltu ভাই থামালো — "না। **এটাই সবচেয়ে বড় ভুল যেটা মানুষ করে।**

সিদ্ধান্তটা পুরো সিস্টেমের জন্য একটা না। **প্রতিটা feature-এর জন্য আলাদা।**

তুই নিজেকে একটাই প্রশ্ন কর — *এই নির্দিষ্ট জায়গায় ভুল তথ্য দেখালে কী ক্ষতি, আর সেবা বন্ধ থাকলে কী ক্ষতি?*"

তানহা বসে তার প্রতিটা feature ধরে ধরে হিসাব করলো:

| Feature | ভুল তথ্যের ক্ষতি | সেবা বন্ধের ক্ষতি | সিদ্ধান্ত |
|---|---|---|---|
| নোট পড়া, তালিকা দেখা | ২ সেকেন্ড পুরনো তালিকা — কিছুই না | user চলে যাবে | **AP** (সেবা) |
| Download সংখ্যা | ১২৪০ না দেখিয়ে ১২৩৮ — কিছুই না | বিরক্তিকর | **AP** |
| Search | কয়েক সেকেন্ড আগের ফলাফল — চলবে | সবচেয়ে ব্যবহৃত feature বন্ধ | **AP** |
| নোট আপলোড | দুবার আপলোড হয়ে যেতে পারে | user ক্ষুব্ধ হবে | **AP** + পরে duplicate মুছে দেওয়া |
| **Premium payment** | **টাকার হিসাব ভুল — সর্বনাশ** | user একটু অপেক্ষা করবে | **CP** (সঠিকতা) |
| **সীমিত আসনের কোর্সে ভর্তি** | **৫০ আসনে ৫১ জন ভর্তি — বিপর্যয়** | কয়েক মিনিট দেরি | **CP** |

**লক্ষ্য করো — একই অ্যাপের ভিতরেই দুই রকম সিদ্ধান্ত।**

তানহা তার payment আর ভর্তির অংশটা এমনভাবে লিখলো যে network সমস্যা হলে সেটা সোজা বলে দেয় *"সাময়িক সমস্যা, একটু পরে চেষ্টা করুন"* — আর বাকি পুরো সাইট দিব্যি চলতে থাকে।

## Amazon-এর বিখ্যাত সিদ্ধান্ত

Boltu ভাই একটা গল্প বললো, যেটা system design-এর ইতিহাসে বিখ্যাত।

"Amazon একবার হিসাব করে দেখলো — 'add to cart' যদি এক মিনিটের জন্যও কাজ না করে, তাহলে তাদের লক্ষ লক্ষ টাকার বিক্রি হারায়।

তাই তারা সিদ্ধান্ত নিলো — **cart কখনোই fail করবে না। কখনোই না।**

কিন্তু তাহলে network ভাঙলে? দুই জায়গায় দুইটা আলাদা cart তৈরি হবে?

তাদের উত্তর ছিল — হ্যাঁ, হবে। আর network ফিরলে আমরা দুটোকে **জোড়া লাগিয়ে দেবো**।

এতে কখনো কখনো user-এর মুছে ফেলা জিনিস আবার cart-এ ফিরে আসে। বিরক্তিকর? হ্যাঁ।

কিন্তু 'cart-এ একটা বাড়তি জিনিস' সমস্যাটা 'cart কাজ করছে না' সমস্যার চেয়ে **হাজার গুণ ভালো**।"

> **এটাই CAP-এর আসল শিক্ষা — এটা technical সিদ্ধান্ত না, এটা ব্যবসায়িক সিদ্ধান্ত।**

## আর তারপর Boltu ভাই আরো একটা বোমা ফাটালো

তানহা ভাবলো ব্যাপারটা এখানেই শেষ। সে বললো — "যাক, network তো বছরে দু-একবার ভাঙে। বাকি সময় তো সব ঠিকই থাকে।"

Boltu ভাই বললো — "আচ্ছা, একটা প্রশ্ন করি। **বাকি ৩৬৪ দিন কী হয়?** সেদিনও কি কোনো পছন্দ করতে হয় না?"

তানহা থমকে গেলো।

"ভাব একটু। তুই ঢাকা থেকে একটা নোট আপলোড করলি। এখন —

**পথ ১:** আমি ইউরোপের সার্ভারেও নিশ্চিত হয়ে তবেই তোকে 'সফল' বলবো।
→ Data সবখানে নিখুঁত ✅
→ কিন্তু ইউরোপে যেতে-আসতে **৩০০ মিলিসেকেন্ড** বেশি লাগবে ❌

**পথ ২:** আমি ঢাকার সার্ভারে লিখেই সাথে সাথে 'সফল' বলবো।
→ দ্রুত ✅
→ কিন্তু পরের কয়েক সেকেন্ড ইউরোপের কেউ ওই নোটটা দেখতে পাবে না ❌

**Network কিন্তু একদম ঠিক আছে। তবু তোকে একটা পছন্দ করতেই হচ্ছে।**"

### PACELC — সম্পূর্ণ ছবিটা

এটার একটা নাম আছে:

> **যদি Partition (P) হয় → বেছে নাও Availability (A) নাকি Consistency (C)**
> **Else (E), মানে স্বাভাবিক সময়ে → বেছে নাও Latency (L) নাকি Consistency (C)**

```
                  Network ভেঙেছে?
                        │
          ┌─────────────┴─────────────┐
         হ্যাঁ                          না
          │                            │
   A নাকি C?                    L নাকি C?
   (CAP এইটুকু বলে)          (PACELC এইটুকু যোগ করে)
```

তানহা বুঝলো — **tradeoff কখনো ছুটিতে যায় না।** সেটা প্রতিদিন, প্রতিটা request-এ আছে।

সে তার সিদ্ধান্তগুলো নতুন করে লিখলো:

| Feature | Partition-এ | স্বাভাবিক সময়ে |
|---|---|---|
| নোট আপলোড | Availability | **Latency** (নিজের অঞ্চলে লিখেই সফল বলো) |
| নোট পড়া | Availability | **Latency** (কাছের replica থেকে পড়ো) |
| Payment | Consistency | **Consistency** (ধীর হোক, নিখুঁত হোক) |

## Consistency আসলে হ্যাঁ/না না — এটা একটা মাত্রা

তানহা আরো একটা জিনিস শিখলো — consistency মানে শুধু "আছে" বা "নেই" না। এর অনেকগুলো স্তর আছে।

**সবচেয়ে কড়া → সবচেয়ে শিথিল:**

**১. Strong Consistency** — যেই লেখা শেষ, সাথে সাথে সবাই নতুনটা দেখবে।
*তানহা এটা ব্যবহার করে:* payment, কোর্সে ভর্তি।
*দাম:* ধীর, আর partition-এ সেবা বন্ধ।

**২. Read Your Own Writes** — অন্তত নিজের লেখাটা নিজে দেখতে পাবে।
*তানহা এটা ব্যবহার করে:* নিজের আপলোড করা নোটের তালিকা (অধ্যায় ৮-এ যেটা ঠিক করেছিল)।

**৩. Monotonic Read** — একবার নতুন জিনিস দেখে ফেললে, পরে আর পুরনোটা দেখাবে না।
*কেন জরুরি:* নাহলে refresh করলে একবার নোট আসে, একবার যায় — user পাগল হয়ে যায়।

**৪. Causal Consistency** — যেসব ঘটনার মধ্যে কারণ-ফল সম্পর্ক আছে, সেগুলো সঠিক ক্রমে দেখাবে।
*উদাহরণ:* কোনো কমেন্টের উত্তর কখনো মূল কমেন্টের আগে দেখাবে না।

**৫. Eventual Consistency** — কিছুক্ষণ পর সব মিলে যাবে, কখন তার নিশ্চয়তা নেই।
*তানহা এটা ব্যবহার করে:* download সংখ্যা, জনপ্রিয় তালিকা।

> **এটাই আসল দক্ষতা** — পুরো সিস্টেমে একটা মাত্রা না বসিয়ে, **প্রতিটা জায়গায় ঠিক যতটুকু দরকার ততটুকু** বসানো।

---

## Quorum — সূক্ষ্মভাবে সুর বাঁধা

তানহা শেষে একটা কৌশল শিখলো যেটা দিয়ে consistency আর গতির মধ্যে **নিজে হাতে সুর বাঁধা** যায়।

```
N = মোট কয়টা copy আছে
W = কয়টাতে লিখলে "সফল" বলবো
R = কয়টা থেকে পড়লে "নিশ্চিত" হবো
```

**জাদুর সূত্র:**

> **W + R > N হলে তুমি কখনো পুরনো data পাবে না।**

কারণ তখন লেখার দল আর পড়ার দলের মধ্যে **অন্তত একজন common** থাকবেই — আর তার কাছে নতুন data আছে।

**N = ৩ ধরে তানহার হিসাব:**

| W | R | মানে | কোথায় |
|---|---|---|---|
| ৩ | ১ | লেখা ধীর, পড়া বিদ্যুৎগতি | পড়া বেশি এমন জায়গায় |
| ১ | ৩ | লেখা বিদ্যুৎগতি, পড়া ধীর | লেখা বেশি এমন জায়গায় |
| **২** | **২** | **ভারসাম্য** | **বেশিরভাগ ক্ষেত্রে** ⭐ |
| ১ | ১ | দুটোই দ্রুত, কিন্তু পুরনো data পেতে পারো | download counter |

তানহা নোটের জন্য W=2, R=2 রাখলো, আর download counter-এর জন্য W=1, R=1।

## তানহা যা শিখলো

**১. CAP-এর আসল প্রশ্ন একটাই** — *network ভাঙলে তুমি কী বাঁচাবে: সঠিকতা নাকি সেবা?*

**২. P বাধ্যতামূলক।** Distributed system-এ CA বলে কিছু নেই।

**৩. সিদ্ধান্তটা পুরো সিস্টেমের জন্য একটা না — প্রতিটা feature-এর জন্য আলাদা।** এটাই সবচেয়ে গুরুত্বপূর্ণ কথা।

**৪. PACELC মনে রাখো** — tradeoff শুধু দুর্যোগের সময় না, **প্রতিদিন** আছে। স্বাভাবিক সময়ে সেটা latency বনাম consistency।

**৫. Consistency একটা মাত্রা, হ্যাঁ/না না।** যেখানে যতটুকু দরকার ততটুকু নাও।

**৬. আর সবচেয়ে বড় উপলব্ধি —** এই সিদ্ধান্তগুলো আসলে technical না, **ব্যবসায়িক**। *"ভুল দেখালে কী ক্ষতি?"* — এই প্রশ্নের উত্তর একজন engineer একা দিতে পারে না।
